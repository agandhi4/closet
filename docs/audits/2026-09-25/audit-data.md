## 2. Findings, ordered by impact

### Finding 1 — Postgres migration tree is missing every foreign-key index that the SQLite tree has (production is unindexed)
**What:** SQLite's migrations explicitly `create index` on every FK column (`outfit_owner_id_index`, `garment_owner_id_index`, `file_created_by_id_index`, `outfit_garments_outfit_id_index`/`garment_id_index`, `user_device_user_id_index`, `outfit_calendar_outfit_id_index`/`owner_id_index`, `wardrobe_share_grantor_id_index`/`grantee_id_index`). None of these exist anywhere in the Postgres tree or in `.snapshot-postgres.json` — confirmed by inspecting the snapshot's index list per table (only PKs and explicit `@Unique()` constraints show up).
**Where:** compare `src/dal/migrations/sqlite/Migration20251104025338.ts`, `…20260224004611.ts`, `…20260406193247.ts`, `…20260612010037.ts` against `src/dal/migrations/postgres/Migration20260305215234.ts`, `…20260406193304.ts`, `…20260612010041.ts`. Confirmed empty via `src/dal/migrations/postgres/.snapshot-postgres.json`.
**Why it matters:** every one of the query patterns above filters by `owner: { id: userId }`, `grantor/grantee`, `outfit_id`, or `created_by_id`. Postgres, unlike SQLite's ORM-managed indexing here, never auto-indexes FK columns — only PKs and unique constraints get one automatically. Production (which runs Postgres per `CLAUDE.md`) is doing sequential scans on `garment`, `outfit`, `outfit_calendar`, `wardrobe_share`, `file`, and `user_device` for the primary access pattern of the app (per-user scoping) on literally every page load, and the FK cascade deletes (`deleteRule: 'cascade'` on User→Garment/Outfit/OutfitCalendar/File/WardrobeShare/UserDevice) also scan the child table without an index when a user is removed. At household scale (hundreds of rows) this doesn't show up as latency yet, but it's a correctness-of-schema gap, not a performance-at-scale one — the two migration trees are supposed to describe the same logical schema and currently do not. This also means "migrations come in pairs" isn't sufficient as a guardrail; the CI parity check only verifies both drivers apply cleanly, not that they produce equivalent indexes.
**Structural fix:** add `@Index()` on every relation property in the entities (`Garment.owner`, `Outfit.owner`, `File.createdBy`, `OutfitCalendar.owner`/`outfit`, `WardrobeShare.grantor`/`grantee`, `UserDevice.user`) so the schema is declared once in the entity and both migration generators produce matching DDL going forward — instead of relying on driver-specific default behavior that silently diverged. Then generate one more migration pair to backfill the missing indexes on existing Postgres installs (`CREATE INDEX CONCURRENTLY` by hand in the migration body to avoid locking the table on the live homelab instance, since MikroORM's generated `create index` would take a table lock otherwise).
**Effort:** S (index-only migration, no data change) but touches production; verify with `EXPLAIN` on `pgvault-connect closet_db` after deploying.

### Finding 2 — The authenticated user is loaded from the DB twice on every request, from two independently-decoded JWTs
**What:** `ConditionalAuthGuard`/`AuthGuard` decode the `access_token` cookie and call `AuthService.verifyPwf`, which does `User.findOneOrFail({id: payload.userId})` purely to compare the last 8 chars of the password hash. Then `ViewContextService.buildContext`, wired as a Fastify `preHandler` hook that runs on **every** request regardless of route or guard, independently decodes the same cookie again and does a second `User.findOne({id: payload.userId})` to populate `reply.locals.user` for the layout (nav bar, etc.).
**Where:** `src/auth/auth.service.ts:80-87`, `src/auth/conditional-auth.guard.ts:22-40`, `src/view-context/view-context.service.ts:64-75`, wired at `src/main.ts:34-36`.
**Why it matters:** this isn't a page-specific N+1, it's a per-request tax paid by literally every single request the server handles (including static-adjacent ones that hit a controller), doubling both JWT verification and a DB round trip for something that's already been done a few lines earlier in the guard chain. It's also two sources of truth for "is this JWT valid" (`verifyPwf` checks the password fingerprint; `ViewContextService` doesn't), so a password change invalidates the guard's view of the session but not what's shown in the nav until the next request that hits a guarded route.
**Structural fix:** guards run before the `preHandler`... actually the reverse — `main.ts`'s `preHandler` hook is Fastify-level and Nest guards run inside routing, so today the hook always runs first. The right fix is to make user resolution happen once per request and be shared: have the Fastify `preHandler` do the single JWT-verify + single `User.findOne`, stash the resolved `User` entity on `request`, and have `ConditionalAuthGuard`/`AuthGuard` and `ViewContextService` both read from that shared per-request slot instead of each re-decoding the cookie and re-querying. This also removes the current inconsistency where the guard's stricter pwf check and the view-context's looser lookup can disagree.
**Effort:** M (touches the auth guard, the view-context hook, and the `@User()` decorator contract — `Payload` vs a real `User` entity — needs care since downstream code assumes `Payload` shape).

### Finding 3 — `findAvailableFilters` does a second full unfiltered table scan of the same rows the page just fetched, in application code, to compute distinct values
**What:** every wardrobe list/new/edit/clone page calls `garmentService.findAll()` (already scoped, populated, ordered) *and* `garmentService.findAvailableFilters()`, which independently runs `Garment.find({owner: {id: userId}})` — no `orderBy`, no `populate`, but still every column of every row — then does `garments.map(...)` / `new Set(...)` / `.sort()` in JS to get distinct brands/sizes/categories.
**Where:** `src/wardrobe/garment.service.ts:216-244`, called alongside `findAll` at `wardrobe.controller.ts:81-84`, `247-250`, `288-291`.
**Why it matters:** two full scans of the same table for one page render, and the second one deliberately avoids the `archived`/search filters the user applied — it's fetching the *entire* wardrobe every time just to populate three `<select>` dropdowns. This is exactly the kind of "loading full entities where a projection would do" pattern the task called out — a `SELECT DISTINCT brand/size/category FROM garment WHERE owner_id = ?` (or three separate lightweight distinct queries) returns the same three arrays without ever hydrating a `Garment` entity or its `photo` relation.
**Structural fix:** replace `findAvailableFilters` with `EntityManager.getConnection().execute()` (or MikroORM's `qb.select(['brand']).distinct()`) issuing the DISTINCT query directly instead of loading entities to filter in memory. This is the highest-leverage single change in the file: it turns "load N garments, twice, per page view" into "three cheap indexed scalar list queries."
**Effort:** S.

### Finding 4 — Garment/outfit photo create is two independent flushes with no transaction, and no compensation on failure
**What:** `GarmentService.create`/`clone`/`update` call `fileService.storeImageFromFileUpload(...)`, which writes the resized image to disk *and* does its own `em.persistAndFlush(file)` inside `LocalFileService` (`local-file.service.ts:70-76`). Control then returns to `GarmentService`, which builds and separately `persistAndFlush`s the `Garment` row (`garment.service.ts:158`). If the garment flush fails (validation error downstream, DB hiccup, unique constraint), the `File` row and the on-disk WebP it points at are already committed and orphaned — nothing references them, nothing cleans them up.
**Where:** `src/wardrobe/garment.service.ts:129-160`, `src/file/local-file/local-file.service.ts:36-77`.
**Why it matters:** this is the literal "file row + garment row + storage" multi-step-write case the task asked about, and today it's neither atomic nor compensated. For a household app this shows up as slow disk-space leakage rather than user-visible breakage, but it's the textbook argument for wrapping multi-entity writes in a single `em.transactional()` block — and even then, the on-disk file write can't be rolled back by a DB transaction, so the ordering matters: the DB write should happen, and only on success should the file be considered durable, or an orphan-sweep needs to exist.
**Structural fix:** wrap the garment-row + file-row persistence in one `em.transactional(async (em) => {...})` so both succeed or neither does at the DB level (this already fixes the common case: DB validation/constraint failures). For the disk-write side, keep the current order (write file bytes → create File row → create Garment row) but only inside the transaction, and add a scheduled cleanup (or at minimum a startup sweep) that deletes `File` rows / disk files with no owning `Garment`/`Outfit` reference older than e.g. 24h, since a process crash between the two flushes is still possible even with a transaction wrapping the DB half.
**Effort:** M (transaction wrapping is small; the orphan-sweep is a new small piece of infrastructure — worth doing given household photos accumulate over years).

## 3. Things that are fine — leave alone

- **Request-scoped EntityManager / identity map isolation.** `@mikro-orm/nestjs`'s `MikroOrmCoreModule` auto-registers `MikroOrmMiddleware` (`consumer.apply(...).forRoutes(ALL)` in `mikro-orm-core.module.js`), which calls `RequestContext.create(orm.em, next)` per request via AsyncLocalStorage — this is wired automatically since `dal.module.ts` never sets `registerRequestContext: false`, and it applies correctly under the Fastify adapter (Nest translates middleware for both adapters). All the singleton services (`GarmentService`, `WardrobeShareService`, etc.) inject `EntityRepository<T>`, which routes through the ALS-scoped EM, so there's no identity-map leakage across requests. There's also no cron/background job anywhere in the codebase (checked `notification.service.ts`) that would call a repository outside of a request context and silently fall back to the shared global EM that `allowGlobalContext: true` permits — that flag is currently inert risk, not an active leak, though it should stay in mind if a scheduled job is ever added.
- **SQLite WAL mode + busy handling.** `dal.module.ts:97` enables `PRAGMA journal_mode = WAL` on startup, which is the right call for a single-writer household app avoiding `SQLITE_BUSY` under concurrent reads.
- **Ownership checks via load-then-compare rather than WHERE-scoped `findOne`.** `GarmentService.findOne`, `OutfitService.findOne`, `CalendarService.findOneOwned` all load by PK first and then check `owner.id === userId` in code, throwing `ForbiddenException`/`NotFoundException` as appropriate, rather than folding the owner check into the WHERE clause. This is a deliberate, consistent pattern across all three services (not an inconsistency) and is correct: it lets a "not yours" request be distinguished from "doesn't exist" for a sharper 403 vs 404, which the share-permission flows depend on. No change needed.
- **Photo relation populate strategy.** Garment/outfit reads consistently `populate: ['photo']` (and `garments.photo` for outfit-level reads) rather than leaving it lazy and triggering per-row lazy loads in the template — this avoids an N+1 on the one relation every list view actually renders (thumbnails).
