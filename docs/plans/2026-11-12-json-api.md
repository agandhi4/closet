# JSON API: conventions, auth, authorization and sync (#187, epic #186)

Status: approved by the owner 2026-11-12, with every recommended option. Each decision below is marked
**Recommended**; the owner's sign-off turns it into "owner decided <date>". Section 12 lists the
questions only the owner can answer. Docs only: no code lands with this plan.

## 1. What exists

- **Domain functions already exist.** Routes call `queries.ts` / `writes.ts` functions and pass a
  plain model to JSX. The MCP server's 40 tools (`src/web/mcp/tools/`) call the same functions over
  a bearer token and answer JSON. The API is the third caller, not a new backend.
- **TypeBox on every route's input** (`@fastify/type-provider-typebox`, `@sinclair/typebox` 0.34).
  **No route declares a response schema**, so OpenAPI needs new response schemas (section 5).
- **Authorization lives in the callers.** The resolver is one function (`authorizeWardrobe`,
  `src/web/sharing/access.ts`, bound per plugin by `wardrobeGuard` / `garmentGuard`). But the
  refusal itself is decided at each call site. Writers answer outcome unions (`'no-trip'`,
  `'no-outfit'`, `'no-such-outfit'`) and each caller maps them to `HttpError(404, <its own message>)`:
  `trips/routes.tsx:316` and `mcp/tools/trips.ts:122` do it twice, and so do
  `calendar/routes.tsx:335` and `mcp/tools/outfits.ts:184`. 13 route files and 6 tool files build
  403/404s. Owner-only reads scope by `owner_id = userId` in SQL (`findOutfit(db, id, userId)`),
  which is sound, but the "not found" is still raised by the caller.
- **Bearer plumbing.** `config: { bearer: true }` is honoured in three places: the root
  preValidation (no session, no page context), `requireSession`, and the same-origin hook (no
  Origin needed). `personal_access_token` stores the SHA-256 of the token, has
  `revoked_at`/`last_used_at`, and `MAX_ACTIVE_TOKENS` caps it. `updatePasswordHash` already revokes
  every PAT and push device in one statement.
- **Harnesses to reuse.** The integration harness, `test/integration/mcp.ts` (bearer inject),
  `authorization-matrix.ts` with its `authorization-coverage.spec.ts` (enumerates routes through
  `onRoute`), `recordQueries` statement budgets (`build/statements.json`), and the grid's keyset
  `?before=<id>`.
- **Not what #186 assumed.** `updated_at` exists only on `user_device`, `style_profile` and
  `body_measurements`, not on `garment` or the week plan. The shopping list and plans are retired
  (#337): #194's "shopping" is the wishlist inbox. Deletes are hard (`delete(garment|outfit|trip|
capsule|outfitCalendar|tripItem|...)`); archiving is `garment.status`. Money is
  `numeric(10,2)` in the household currency (a string in TypeScript). There is no account
  lockout, only `SIGN_IN_LIMIT`.
- **Promises already made.** `2026-09-28-caching-and-offline.md` section 4 promises one
  trigger-maintained per-owner **revision** that serves both web 304s and native sync, and an
  idempotency convention its web queue adopts. This plan delivers both (sections 2 and 7).

## 2. API conventions (Recommended)

- **Path versioning: `/api/v1`.** At most two versions are live, and the older one carries
  `Sunset` (backend.md). Resources are plural, hyphenated nouns, nested at most two levels:
  `/garments/{id}`, `/garments/{id}/photo`, `/trips/{id}/items/{itemId}`, `/calendar-entries`,
  `/capsules/{id}/members/{garmentId}`. A state transition is a sub-resource, never a verb in the
  query: `PUT /garments/{id}/status`, `POST /garments/{id}/washes`. **Share-aware routes keep
  `?ownerId=`**, as pages and MCP do, so the resolver, its read-ahead (#170) and the matrix's
  `ownerId` via apply unchanged.
- **Feature locality.** API routes live in `src/web/<feature>/api-routes.ts`, beside that
  feature's pages, and register through one `apiPlugin` with prefix `/api/v1`. The pure resource
  mappers sit beside them (`toGarmentResource(detail)`).
- **JSON.** camelCase (as MCP's arguments are). Ids are integers (section 7 explains why not
  uuids). Null fields are omitted. Enums are the stored lowercase strings.
  - **Dates come in two dialects** (data.md §2). A household day is `IsoDate` `YYYY-MM-DD`, never
    sent through a timezone. An instant is ISO 8601 with `Z`. "Today" is the server's
    `todayIn(APP_TIMEZONE)`, which `GET /api/v1/me` reports with the zone. A wear or wash write
    sends an explicit `day`; the server accepts `today-7..today` (caching plan 3b).
  - **Money is a decimal string** (`"12.47"`, backend.md Serialization), which is the column as
    it is. The brief said cents; integer cents would mean a conversion at every boundary for no
    gain (owner decision 4).
- **Lists** answer `{ data: [...], pagination: { nextCursor?, limit } }`. The cursor is opaque
  (base64url of the keyset: the grid's `before` id, or a sort key plus id), and `limit` defaults to
  the grid's page size with a cap of 100. There is no `total`: a count costs a statement, so a
  route that needs one (the grid's count) returns it as its own field.
- **Errors: RFC 9457 `application/problem+json`** (backend.md), not the issue's
  `{ error: { code, message } }`. The body is `{ type, title, status, detail, code, requestId }`.
  - `code` is a stable machine string that the client switches on: `not_found`, `forbidden`,
    `validation`, `unauthorized`, `rate_limited`, `conflict`, `stale`, `busy`, `internal`.
  - `detail` is the page's own i18n message ("Garment not found").
  - `HttpError` gains an optional `code`, defaulted from the status. `OwnerLockTimeout` is `busy`
    with `Retry-After`.
  - The root error handler picks the shape by the route's surface (section 3). Validation is a
    400 with `errors: [{ path, message }]`, the same status a page gives, so the two surfaces agree.
  - Unknown `/api/*` paths get the problem 404, not the HTML not-found page.
  - A 500 carries no detail.
- **Idempotency: client ids, not a receipt store.**
  - Every create that a native client may make offline takes an optional `clientId` (uuid). It is
    stored in a nullable `client_id uuid` column, unique on `(owner_id, client_id)` where it is not
    null. A retry answers 200 with the existing row instead of 201.
  - Every other write is idempotent by meaning: PUT/PATCH set state (`packed: true`, `status`,
    explicit `day`), and DELETE of a missing row is a 404 that the client treats as done.
  - `Idempotency-Key` is accepted and logged, for traceability as in caching plan 3b, but never
    stored. Closet has no Redis and wants no receipt table. This is a convention delta and gets its
    own decisions.md entry.
- **Conditional requests.** Arrive with #196's revision:
  - A single resource answers `ETag: "r<revision>"`. `If-None-Match` gives a 304, and the token
    read fetches the revision, so the 304 costs no extra statement.
  - A write may send `If-Match` and gets a 412 `stale` if the row has moved on.
  - `/today` and anything carrying weather send no ETag (they depend on the day and the forecast).
  - Lists send none either: `/changes` does that job.
- **Rate limits.**
  - `API_LIMIT`: 120 a minute per token, a preHandler after authentication, as `MCP_LIMIT` is.
  - Routes that already have a budget share it with their page twin, through one checker per
    budget: `LINK_IMPORT_LIMIT`, `WEATHER_SEARCH_LIMIT`, and `ACCOUNT_LIMIT` on anything that checks
    a password.
  - The token login uses `SIGN_IN_LIMIT`.
  - A 429 is a problem body with `Retry-After`.

## 3. Auth: device tokens and the surfaces (#189)

- **One credential table.** `personal_access_token` gains
  `kind text not null default 'mcp' check (kind in ('mcp','device'))`; `name` is the device name.
  - `authenticateToken(db, token, kind)` refuses the wrong kind, so a leaked MCP token in a Claude
    config cannot drive `/api`, and a device token cannot call `/mcp`.
  - `MAX_ACTIVE_TOKENS` counts each kind separately.
  - A device login past the cap revokes that user's least-recently-used device token, and logs it.
- **Login.** `POST /api/v1/auth/token` takes `{ email, password, deviceName }` and answers
  `{ token, tokenId }` with `Cache-Control: no-store`.
  - It is public, under `SIGN_IN_LIMIT`, and runs the hash even for an unknown email (timing). It
    logs as the login route does.
  - `DELETE /api/v1/auth/token` revokes the calling token.
  - Profile gets a "Devices" list (name, last used) with revoke: web-only, beside Agent Access.
  - **No expiry and no refresh tokens.** A token is checked against its row on every request, so
    revocation is immediate. That is the cookie's model (a year-long JWT checked against the user
    row), and rotation would buy nothing here (owner decision 8: an idle expiry instead).
- **Step-up still applies.** A token is never enough for an action the pages gate behind the
  current password: changing a password or email, creating a PAT, or deleting the account.
  - v1 exposes none of these (web-only, section 6).
  - Any that is added later takes `currentPassword` in the body, under `ACCOUNT_LIMIT`, and checks
    it with `verifyPassword`, exactly as its page does.
- **Revocation.** A new password already revokes every PAT, device tokens included, and keeps that.
  - `updatePasswordHash` gains a `keepTokenId`, as push has `keep`, so a device that changes its
    own password stays signed in (only once the API offers that route).
  - APNs registrations hang off the token (section 8), so they go with it.
- **Surfaces replace the `bearer` flag.** The flag becomes `config.surface: 'page' | 'mcp' | 'api'`.
  - `apiPlugin` stamps `'api'` on every route it registers (an `onRoute` hook), so no route can
    forget it.
  - The root preValidation never reads the cookie on `mcp`/`api`.
  - The error handler and the not-found handler answer problem+json on `api`.
  - `requireSession` defers to the plugin's token hook, which answers a missing, bad or revoked
    token with 401 `unauthorized` and `WWW-Authenticate: Bearer realm="closet"`.
  - A token is never read from the query string; a request that puts one there is a 400.

## 4. Authorization into the domain functions (#188)

- **The shape.** One `Actor` per call, `{ userId, shareReadAhead? }`, built once by
  `actorOf(request)` for pages and `actorOf(ctx)` for MCP and the API.
  - `authorizeWardrobe` takes an `Actor` instead of `Requester`, so no domain function sees a
    `FastifyRequest`. Read-ahead survives: the page actor carries it, so each request still costs
    the statements it costs today.
  - A domain function takes the actor and the address, and enforces access itself:
    `updateGarment(db, actor, { ownerId, id }, input)`, `scheduleOutfit(db, actor, ...)`.
  - It throws a typed refusal (`NotFound('garment')`, `Forbidden()`, both `HttpError`s with a
    `code`), whose message comes from one table per resource. It no longer returns `'no-outfit'`
    for each caller to translate.
  - Callers shrink to: parse, call, render. Pages get `ErrorPage`, MCP a tool error with the same
    message, the API a problem body.
- **Where checks stay in the caller.** Rate limits, the step-up password and the session gate are
  request concerns and stay put. Each one left in a handler gets a one-line reason (#188 acceptance).
- **The guard comes first.** `make guard-check` gains a shrink-only `known` list (as
  `layers.conf` has) of `new HttpError(40[34]` sites in `routes*.ts(x)` and `mcp/tools/`. Each area
  PR deletes its lines, and a new one fails ci-quick.
- **Order** (one PR per area, the matrix unchanged as the proof; new unit specs call the domain
  function with a stranger and a VIEW grantee):
  1. `Actor`, refusal codes and the guard (S)
  2. garments: guard, `requireGarment`, writes, status, repairs (L)
  3. capsules and wishlist (M)
  4. outfits, calendar and week plan, the owner-only outcome unions (M)
  5. trips and packing (M)
  6. sizes, style and sharing (S)

## 5. OpenAPI and parity (#190, #191)

- **The spec.** `@fastify/swagger` is a **devDependency**. `npm run api:spec` registers
  `apiPlugin` on a bare Fastify instance (no listen) and writes `src/web/api/openapi.json`
  (OpenAPI 3.1; TypeBox 0.34's JSON Schema maps onto 3.1 directly, nullable unions included).
  `GET /api/v1/openapi.json` serves that committed file, so what is served is what was reviewed,
  and there is no runtime dependency.
- **Every `/api/v1` route declares** an `operationId`, `tags`, and a response schema for each 2xx
  plus the shared problem schema. Fastify then serializes through the schema, which also drops any
  column a mapper leaks.
- **The drift test** (`api-spec.spec.ts`, unit tier if the plugin registers without a database,
  otherwise integration) regenerates the spec and diffs it with the committed one. It also asserts
  the declarations above for every route. A contract change becomes a reviewed diff.
- **Parity rule (AGENTS.md).** A feature is done when its domain function has a page caller, an API
  caller, and an MCP caller where an agent needs it.
- **What the parity test asserts.** It enumerates routes with `onRoute`, as
  `authorization-coverage.spec.ts` does, on an app with every flag on.
  1. Every non-GET page route declares exactly one of `config.operation` (an `OperationId` from
     `src/web/operations.ts`, a typed const list, so a typo fails `tsc`), `config.webOnly`
     (a reason string), or `config.apiPending` (an issue number).
  2. Every `operation` a page declares is the `operationId` of at least one API route, and every
     API `operationId` is in the list.
  3. For each matrix case on a page route with an operation, the same actor (stranger, VIEW
     grantee, MANAGE grantee) on the API twin gets the same status. This is refusal parity, the
     behavioural proof that both call the one function.
  4. The `apiPending` count only shrinks: it is a `make ci-metrics` key, `api.pending_routes`.
- **Out of scope for the test.** GETs (a page composes several reads) and MCP coverage, which is
  listed but not asserted (#191 out of scope). #191 marks every current write route `apiPending:
<192..195>` or `webOnly`; the area issues turn pending into operations.

## 7. Sync model (#196)

- **Ids: keep `serial`, add `client_id`** (Recommended over a `uuid public_id` everywhere).
  - Rekeying 35 tables and every foreign key buys only offline creates, and `client_id` gives
    those.
  - The client keys its local rows by `clientId` until the create returns the server `id`. A
    retried create returns the same row.
  - `client_id` goes only on tables a client creates offline: `garment_wear`, `outfit_calendar`,
    `trip_item`, `outfit`, `garment`, `trip`, `capsule`, `brand_size`. It is one id strategy, as
    data.md asks; `client_id` is an external key.
- **The revision, not `updated_at`, is the cursor.** Timestamps are unsafe cursors: a transaction
  that started earlier commits later, and two writes can land in the same millisecond.
  - `user.revision bigint` is bumped by a trigger on every synced write. Every synced row gets
    `revision bigint not null default 0`, set to the owner's new revision.
  - The bump is an `UPDATE` of the owner's row, which takes the same `FOR NO KEY UPDATE` lock as
    `lockOwner`. Per owner, revisions therefore commit in order: a reader never sees revision 9
    before 8.
  - The cost is that one owner's writes serialize, which `ownerTransaction` already does for the
    calendar and plans. It adds **no round trip**: the bump is in the trigger.
  - A cross-owner transaction (accepting a share) must lock owners in id order, or skip the bump
    because shares are not synced data.
  - `updated_at` is added too, per data.md, as information, never as a cursor.
- **Resources sync as aggregates.** A child row's trigger bumps its parent:
  - `outfit_slot` bumps the outfit;
  - `trip_item`, `trip_outfit` and `trip_garment_packed` bump the trip;
  - `capsule_garment` bumps the capsule;
  - `week_plan_entry` bumps the week plan;
  - `garment_repair` and the garment's `file` (photo, cutout status, `version`) bump the garment.
  - The synced roots: garment, outfit, calendar entry, wear, selfie, capsule, trip, week plan,
    style profile, measurements, brand size, week template.
- **Tombstones are a table, not `deleted_at`** (data.md: "sync tombstones are not soft delete"):
  `sync_tombstone(owner_id, resource, resource_id, client_id, revision, deleted_at)`.
  - An `AFTER DELETE` trigger on each root writes it, so cascades are covered and no writer can
    forget one.
  - It cascades from `user`, so account deletion erases the tombstones too.
  - The nightly maintenance prunes it after 90 days and records `user.sync_floor`, the newest
    pruned revision.
  - An archived garment is an update (`status`), not a tombstone.
- **The changes feed.** `GET /api/v1/changes?cursor=<opaque>&limit=`.
  - The cursor is `{ <ownerId>: revision }`: the caller's own data, plus each shared wardrobe
    (garments and capsules only, the share-aware set).
  - It answers `{ changes: [{ resource, id, revision, data }], deletions: [...], cursor, more }`.
  - It is keyset by revision through an `(owner_id, revision)` index on every root, declared in
    `schema.ts`.
  - A cursor below `sync_floor` is a 410 `cursor_expired`, and the client does a full sync. A share
    that is gone drops that owner from the cursor and lists it in `revokedWardrobes`.
- **Conflicts.**
  - The default is last write wins **per field**: a PATCH carries only the fields that changed,
    which is what the page autosave already does per control.
  - `If-Match` makes a write strict (412 `stale`). It is optional everywhere and required nowhere
    in v1.
  - The week plan keeps its rule: a person's write sets `planned_by = user`, and the planner never
    overwrites one. Between two devices, last write wins per entry.
  - The packing list is set-state per item, so a repeated tick is a no-op.
  - An update to a deleted row is a 404, and the client drops it (the caching plan's 3b table).
- **Photos do not sync as bytes.** Resources carry the immutable `/file/*?v=` URLs. A new
  `version` is a new URL, so a client caches forever and fetches lazily. A photo taken offline is
  uploaded after its garment's create (by `clientId`) with `PUT .../photo`, which is idempotent.
- **What the schema change costs.**
  - Migrations: one expand-only migration (`revision`, `updated_at` and `client_id` with their
    indexes, `user.revision`/`sync_floor`, `sync_tombstone`) and one hand-written for the triggers,
    since Drizzle does not model triggers.
  - `migrations.spec.ts`'s drift check cannot see triggers, so a new `sync-triggers.spec.ts` reads
    `pg_trigger` for every synced table. Backfill: `revision 0`, `updated_at = created_at`.
  - The issue says "reversible": the repo is forward-only, and expand-only means the previous
    build runs on the new schema.

## 8. Push for a native client (#197)

- Web Push stays for the PWA. APNs is a second transport behind the same sender:
  `createPushSender` dispatches per device.
- `user_device` gains `transport ('webpush'|'apns')`, a nullable `apns_token`, and `token_id`
  (a foreign key to the device token). Reminders, `muse_rounds`, `push_reminder` claims and
  `sendEach` then work unchanged, and each notification is still defined once.
- `POST /api/v1/push/devices` upserts it. Revoking the token deletes its devices, in the same
  statement as `revokeDevicesStatement`.
- **It needs:**
  - an Apple Developer account and a `.p8` key in sops (`APNS_KEY_ID`, `APNS_TEAM_ID`,
    `APNS_KEY`);
  - an HTTP/2 client to `api.push.apple.com`;
  - a guard-check decision for that call, because `createOutboundFetcher` is the only sanctioned
    path and it speaks HTTP/1.1.
- **Recommended: later.** Nothing in #188 to #196 depends on it; a native client can start with
  background refresh plus `/changes`.

## 9. Security review points

- **CSRF does not apply.** `/api` never reads the cookie, so a cross-site page has no ambient
  credential to ride. The same-origin hook treats the `api` surface as it treats `bearer`: no Origin
  passes, and a present foreign Origin is still a 403 (DNS rebinding). That covers the public
  login route too: it sets no cookie, and its JSON answer is unreadable cross-origin.
- **No CORS.** No `Access-Control-*` header is ever sent. A browser preflight for `Authorization`
  fails, so no web page can call the API. The PWA never calls `/api`: the server owns its HTML.
- **Exposure.** Tailnet only, like the app, unless the owner chooses a public host through a gate
  as `/mcp` has (owner decision 6). If public, tokens are the whole gate, as for `/mcp`.
- **Logging.**
  - The `Http` access line, through `loggableUrl`, gains `user_id` and `token_id` (the row id) on
    `api`. The logger already redacts `authorization`.
  - `api.spec.ts` asserts that no token or prefix reaches a log line, as `mcp.spec.ts` does.
  - Login logs the outcome and the client address, never the password or the token.
- **No email on any public answer.** Responses are serialized through their schema, so an unlisted
  column cannot leak.

## 10. Tests and budgets

- **Integration tier only. No Playwright scenario** (there is no browser surface).
  - The harness gains `t.api(token)`, cloned from `mcp.ts`.
  - API matrix cases join the **existing** `authorization-<group>.spec.ts` files as a third via,
    so no new scratch databases are cloned and ci-db stays inside 110 s.
  - Each area adds one happy-path spec per resource group.
  - #196 adds the sync scenario: sync, edit and delete from another session, then `/changes` holds
    exactly the delta; a retried `clientId` makes no duplicate.
- **Statement budgets.**
  - Every API route runs inside a `recordQueries` block (`api-statements.spec.ts`), so it lands in
    `build/statements.json` as `<METHOD>:/api/v1/...`.
  - Each is pinned at or below its page twin's count: token auth is one statement, as the session
    is, plus the last-use write once a minute.
  - `/changes` is one statement per page (a `union all` of the roots and the tombstones).
- **Collected-count floors** rise with each area PR, in the same PR.
