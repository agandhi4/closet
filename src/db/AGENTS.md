# Database

How to change the schema is in the root `AGENTS.md` (Changing the schema). This is the rest.

- **Data**: PostgreSQL only (18 in production on pgvault and in pgvault-dev locally, 17 in CI). **Drizzle ORM owns the schema, the migrations and every query** (`src/db/schema.ts`, `drizzle/`, applied at boot by `src/db/migrate.ts`; see Changing the schema). MikroORM left the app on 2026-09-26 with the garment port; its frozen migration tree lives in `test/support/legacy-migrations/`, run only by `test/support/legacy-migrations.ts` to build production-shaped databases for the migration specs (`@mikro-orm/core`, `/postgresql` and `/migrations` are devDependencies for that alone). SQLite was dropped on 2026-09-25: its test tier passed on behavior production never had (case-insensitive `LIKE`, unbounded `varchar`, a drifted `color` type) and its migration tree wiped rows.

**Pending migrations run in one transaction, all files together** (drizzle-orm's migrator). A failed batch leaves nothing behind, and `CREATE INDEX CONCURRENTLY` cannot run inside it. The tables are household-sized, so a plain `CREATE INDEX` holds its write lock for milliseconds; if a table ever grows to where that matters, build the index in a non-transactional step added to `runMigrations` after `migrate()` (under the same lock), not in a migration file.

**Indexes, as audited on 2026-09-28** (#175, production's statistics read in a read-only session). Every foreign key leads an index or a unique constraint. The indexes with no scans are unique constraints (they enforce, they are not read), primary keys, and the indexes of tables still empty in production (`order_email`, `order_item`, `pending_photo`); none was dropped on that alone. The one dropped, `wardrobe_share_grantor_id_index`, duplicated the leading column of `wardrobe_share_grantor_id_grantee_id_unique`. Sequential scans dominate only tables of a few hundred rows, where the planner is right to choose them. `pg_stat_statements` is not installed on pgvault. Named prepared statements save about 0.5 ms of planning on the grid page and 0.1 ms on the session lookup, noise against a round trip to pgvault: #220.

**Timeouts** (#134, `DbTimeouts` in `client.ts`, sent as startup parameters): one stuck transaction must not wedge an owner's writes (the owner lock, Calendar). `createDb` opens the server's pool with `SERVER_TIMEOUTS`: `statement_timeout` 15 s, `idle_in_transaction_session_timeout` 30 s (Postgres ends the session of a transaction left waiting on the app between statements: a request stuck on I/O inside it, a client gone mid-way; its next statement fails, the pool drops the connection). The nightly reconciliation shares the pool: its statements are short, household-sized queries. `lock_timeout` is not a pool setting: every form of the owner lock sets it (`OWNER_LOCK_TIMEOUT_MS`, 5 s, `set_config(..., true)`, i.e. `SET LOCAL`, in the lock's own statement, #158; `lockOwner` and each folded one, PR #537), so only owner writers fail fast on a lock: a 55P03 is `OwnerLockTimeout`'s 503 (`describeError`, `src/web/errors.tsx`, for a folded one; `ownerTransaction` names its writer). **Longer, explicit**: `MAINTENANCE_TIMEOUTS` (10 min statement, 5 min idle in transaction) for the boot's migrations (`runMigrations`, `requireCurrentSchema`; the advisory-lock wait of an overlapping deploy counts as a statement) and every CLI (`runCli`'s pool: the seed's one-transaction persona, reconciliation, set-password). The client's own limits ride in the same `DbTimeouts` (#643): `connectMs` (`connectionTimeoutMillis`, 5 s: also pg-pool's wait for a free connection, `PoolExhausted`), `queryMs` (`query_timeout`, just above `statementMs`, so a live server's 57014 always fails first; node-postgres neither cancels the statement nor ends the connection, so the pool's `TimedClient` ends it at once, or a transaction's ROLLBACK waited behind it and the busy connection went back to the pool) and TCP keepalive (60 s), for a host that stops answering, which no server-side limit ends. The cutout listener opens with `SERVER_TIMEOUTS` too; `connectionOptions` without timeouts keeps every default (the specs' own clients). `test/integration/db-timeouts.spec.ts`, `database-unavailable.spec.ts`.

**The database out of reach is a typed outcome** (#643). A connection the pool cannot open fails as `DatabaseUnreachable` (`TimedPool.connect`, both of Drizzle's paths), so the refused socket is known to be the database's; `isDatabaseUnavailable` (`errors.ts`) adds SQLSTATE class 08 and 57P01-03, and a query whose connection was lost (an errno or node-postgres's codeless messages, only under a `DrizzleQueryError`). The web layer answers it as `DatabaseUnavailable`, a 503 `busy` with `Retry-After` (`describeError`), captured once per outage (`DatabaseOutage`, `src/web/errors.tsx`, ended by the first time the database answers again: createDb's `onAnswer`, a connection opened or one given back with its last query answered). **A full pool is not an outage**: pg-pool's wait for a free connection is bounded by the same `connectionTimeoutMillis`, and its own `timeout exceeded when trying to connect` (no socket opened) is `PoolExhausted`, answered `DatabasePoolBusy` (503 `busy`, `SERVER_BUSY`, `Retry-After: 1`), never captured, the outage left alone. Every cause-chain walk is `src/driver-error.ts` (shared layer), which `errorFields` reads too: the innermost `code` and the reason first.

**How `src/db/migrate.ts` adopts a MikroORM-era database** (production's first Drizzle boot). All of it runs on one connection holding `pg_advisory_lock(hashtext('closet:migrations'))`, so two servers on one database (an overlapping deploy) never migrate at once; the second waits, then finds nothing to do.

- First (before the legacy step, so a refusal writes nothing), a database whose newest row's `created_at` is not in this build's journal is refused: `SchemaAheadError` (#651), the image older than the database. `schemaState` is the one three-state rule (behind, current, ahead) the boot, `requireCurrentSchema` and `/health/ready` share; a migration is identified by `created_at` (the journal `when`, drizzle's own key), never `hash`. The documented manual rollback deletes the newer rows after undoing their DDL, which makes the older image current again (docs/operations.md#migrations-and-rollback).
- `mikro_orm_migrations` exists: its rows must include `LAST_LEGACY_MIGRATION` (`Migration20260926021506`, the newest file in `test/support/legacy-migrations/`), or boot fails with `LegacyMigrationsIncompleteError` (boot a pre-Drizzle build once to finish them). Then, if `drizzle.__drizzle_migrations` has no row for the baseline (`drizzle/0000_baseline.sql`, the full schema as MikroORM left it), the runner inserts the row drizzle's migrator would have written (hash and `created_at` from drizzle-orm's own `readMigrationFiles`) without running the SQL.
- No `mikro_orm_migrations`: a fresh database; the baseline runs like any migration.
- Then drizzle's `migrate()` applies anything newer. The log says which: baseline recorded, `Applied N Drizzle migration(s)`, or `Schema up to date`.
- `mikro_orm_migrations` stays in legacy databases (hidden from drizzle-kit by `tablesFilter`). MikroORM is gone from the app; once production is known to be past the baseline, the legacy check, `test/support/legacy-migrations*` and the three `@mikro-orm/*` devDependencies go too.

## Layout

```
    schema.ts          Every table, index, constraint and relation (the source of drizzle/ migrations)
    client.ts          dbConfig(config), createDb(): one pg Pool (max 10, min 2) + drizzle(), with its
                       DbTimeouts (see Timeouts). Db, and Queryable (Db or a transaction) for writes
                       that must commit with others; sslOption(): DATABASE_SSL's mode as pg's `ssl`
                       (`false` when off: undefined would let PGSSLMODE in)
    errors.ts          isUniqueViolation, isLockTimeout, isDatabaseUnavailable: a driver error through
                       drizzle's cause chain (driverError, src/driver-error.ts); DatabaseUnreachable, PoolExhausted
    owner-lock.ts      ownerLockCte / ownersLockCte (a subquery or ids) / ownerLockSql / ownersLockSql: the owner lock's one statement shape,
                       folded into a writer's first statement, marking the transaction once the row is
                       held (Calendar's Owner lock; the sync triggers read the mark)
    sync-tables.ts     SYNC_ROOTS / SYNC_CHILDREN: the synced tables as data, what the sync triggers
                       (drizzle/0052) stamp and sync-triggers.spec.ts holds pg_trigger to
    sync-epoch.ts      bumpSyncEpoch(): a new history for the changes feed after a restore (#652;
                       the post-restore command, #653), every device's cursor then a 410
    select-scalars.ts  selectScalars(): independent scalar subqueries (counts, JSON lists) in one
                       statement, one round trip (the wardrobe grid's context, #159)
    migrate.ts         runMigrations(): boot-time runner (ahead refusal, legacy adoption, advisory lock);
                       requireCurrentSchema(): the CLIs' check instead of migrating; schemaState()
```

## The owner lock's statement (#196a)

- **Every write to a synced table takes its owner's lock before any other row lock** (Calendar's Owner lock, extended): the roots and children of `docs/plans/2026-11-12-json-api.md` §7, listed in `src/db/sync-tables.ts` (garments, outfits and slots, entries, wears, selfies, capsules and members, trips and their rows, the week plan and template, sizes, the style profile, measurements, a garment's photo row). The sync triggers bump the owner's revision with an UPDATE of the user row from inside the write, after the row is locked; a writer that held a garment, trip or photo row first would deadlock with one that holds the owner and waits for that row (`pickIdea`, `deleteOutfit`'s cascade into a trip, `swapPhoto`). Rows outside the synced tables count too when the owner's holder deletes them: every taker of a pending row (a garment's or a look's save, a discard) takes the owner before the photo name and the row (`lockOwnersAndPhotoName`, the only way to lock a name), as account deletion does.
- **One global order: every account a transaction writes rows of, locked in one statement, ascending, before any other lock** (#544). A MANAGE grantee's save of their pending photo writes the uploader's pending row and the owner's garment and `file` row, so it locks both (`lockOwnersAndPhotoName(tx, [ownerId, userId], name)`); account deletion locks itself and the owners of garments showing its photos in one set (`ownersLockCte`), never itself first and the others after: holding 5 while waiting on 3 deadlocks a save holding 3 and waiting on 5. A multi-account lock is true only when **every** account was locked (one gone is a refusal, not an unlocked write). Why no pair deadlocks: every owner-lock wait is in a first statement, and after it each writer only waits on rows of accounts it holds.
- **A delete that must see what the lock's waiters committed runs in the statement after the lock, never folded into it.** Under READ COMMITTED a statement reads with the snapshot taken before its InitPlan waited: account deletion's `file` delete, folded into its lock, missed the row a save committed while it waited, and the user's cascade dropped it with its bytes left behind (#544). `deleteUserAndFileRows` locks alone, then deletes in one statement that re-reads the owner set; an owner it did not lock deletes nothing, and `deleteAccount` locks again (3 attempts; no writer since #40 makes such a row). A folded lock stays right for a write gated on its own locked row (`lockGarment`, the cutout row: EvalPlanQual re-reads that row), not for a scan of rows others insert.
- **A writer outside `ownerTransaction` folds the lock into its first statement** (`owner-lock.ts`), so it costs no round trip: `ownerLockCte` + `ownerLocked` (an uncorrelated count of the CTE's rows, a one-time filter run before the scan; never `exists` or a `limit`, which stop at the first of several owners) or `lockedOwnerId` (an insert's owner column) in a builder, `ownerLockSql` (or `ownersLockSql`, a subquery's owners) + `OWNER_LOCKED` in SQL, `ownersLockCte` for several owners (id order) or one learnt from the row. `lockGarment`, `lockTrip`/`lockedTripCte`, `lockMembers`, `lockCutoutRow` and `lockCutoutRows` take it that way, so their callers do; `owner-lock.spec.ts` EXPLAINs each.
- **The mark is set only once the row is held.** The statement sets `closet.locked_owners` (SET LOCAL) in a select above its LockRows, over the row returned, never in the scan below it where `lock_timeout` must sit. The sync triggers raise `owner lock not held: a write to <table> for owner <id>` on a synced write in a transaction without the owner's mark (an owner that no longer exists passes: its cascade), so every tier proves every writer; spec fixtures write through `asFixture` (`test/integration/harness.ts`). It catches a writer that forgot the lock, not one that sets the mark by hand: forgetfulness, not malice.
- **A photo's owner is fixed for its row's life** (`garmentOwnersOf`, `src/cutout/queries.ts`): a garment only points at a `file` row its own transaction inserted, and the row goes in the transaction that stops pointing at it, so the cutout writers lock the owner they read before the lock; `applyCutoutEvent` checks it again in its write and throws if it moved.

## The sync triggers (#196a-2)

`drizzle/0052_sync-triggers.sql`, hand-written (`drizzle-kit generate --custom`; drizzle-orm splits a file only at `--> statement-breakpoint`, so a `$$` body is one statement). The drift test cannot see functions or triggers: `test/integration/sync-triggers.spec.ts` holds `pg_trigger` to `sync-tables.ts`, so a new synced table changes both, plus a new migration (the shipped one is frozen).

- **One revision per transaction per owner.** `closet_sync_revision(owner, table)` checks the mark, then returns the owner's cached revision or bumps `user.revision` once and caches it in `closet.revision_<id>` (SET LOCAL). A GUC name part may not start with a digit, so the plan's `closet.revision.<id>` is invalid. A savepoint rolled back reverts the bump and the cache together. An account's BEFORE DELETE sets its cache to `gone`: its cascades stamp nothing and write no tombstone (a tombstone for a deleted user would fail its foreign key).
- **Roots** stamp `revision` (and `updated_at` on update) in a BEFORE row trigger; an AFTER DELETE row trigger writes the `sync_tombstone`, cascades included. **Children** (and a garment's photo: only its version or cutout status) touch each parent row once per statement (`updated_at = now()`, AFTER statement triggers over transition tables, one per event), and the parent's own trigger stamps it. The week template stamps `user.week_template_revision`. A no-op upsert still bumps: a spurious change is harmless, a missed one is not.
- **`client_id` lives only on root tables** (the ones with tombstones). A child table (`trip_item`) gets one only together with a tombstone trigger, or a replayed create could resurrect a deleted row.
- **A replayed create never resurrects.** An insert whose `client_id` has a tombstone for its owner and table raises SQLSTATE `CL410` (`isDeletedClientId`, `errors.ts`; the route's 410 `gone`). The check is in the trigger, not the writer's statement: a trigger's query takes a fresh snapshot, so it sees a tombstone the owner lock's holder committed while the writer waited, which the writer's own READ COMMITTED snapshot (taken before the wait) does not (`queued-writes.spec.ts` interleaves it). A writer whose create carries a client id names the day's own arbiter in `on conflict (...)`, so a client id taken by another row is a unique violation (409), never a silent no-op (`setWoreToday`).

## Gotchas

- **A connection can die while checked out, and an unheard 'error' kills the process.** pg-pool listens for a connection's `error` only while it is idle in the pool; `idle_in_transaction_session_timeout` ends a session mid-transaction, and node-postgres emits `error` on that client with no query to fail. `createDb` gives every connection its own listener (`pool.on('connect')`); keep it for any new pool or long-lived client.
- **A numeric column's default is written as SQL** (``.default(sql`'0'`)``, `user_weather.temperature_offset`): Postgres reads a numeric default back as the literal `'0'`, so a plain `.default(0)` shows as drift in `migrations.spec.ts`.
- **Postgres' `least()` and `greatest()` ignore NULL arguments.** `least(quantity, wears / null)` is the quantity, not null, so a garment that never needs a wash came out fully dirty until the SQL wash rule (`dirtyCopiesSql`) used a CASE; `wears.spec.ts`'s SQL-against-TypeScript case table caught it. Compare any SQL form of a pure rule against the rule the same way.
- **A unique violation is answered only for the constraint the caller names.** `isUniqueViolation(error, constraint)` (`src/db/errors.ts`) takes the constraint (`UniqueConstraint`: the names are constants beside their indexes in `schema.ts`) and is false for any other, so the caller rethrows. Matching any `23505` once turned the plans' one-active race into "a plan with this name already exists". A new writer that answers a violation with a message adds its constraint to `UniqueConstraint`.
- **Drizzle's index `.desc()` is `DESC NULLS LAST`, not SQL's `DESC`.** drizzle-orm's `ExtraConfigColumn` defaults `nulls` to `last` whatever the order, while a query's `desc(col)` is plain `DESC` (NULLS FIRST in Postgres). A btree is only read in order for the exact order or its full reverse, so the garment keyset indexes (`id DESC NULLS LAST` from MikroORM to 0031) never served an `orderBy(desc(garment.id))` read in order: at 32,000 garments the grid scanned `garment_pkey` backward past every other owner's garments (2.3 ms against 0.16 ms, #175). A descending index column is `.desc().nullsFirst()`, which generates `DESC NULLS FIRST` and reads back as `DESC`. `test/integration/garment-index-order.spec.ts` EXPLAINs the grid page and fails on a plan that does not read `garment_owner_id_status_id_index` in order.
- **Indexes and constraints are declared in `src/db/schema.ts`, never only in a migration file.** `drizzle-kit generate` diffs snapshots, not the database, so DDL hand-added to a migration is invisible to every later diff and the drift test reports it. Postgres does not index foreign keys on its own. `test/integration/migrations.spec.ts` lists the expected index names.
- **`patches/drizzle-kit+0.31.11.dev.patch` fixes `pushSchema` (`drizzle-kit/api`), which the drift test depends on.** Unpatched, its Postgres introspection drops query parameters (the composite primary key lookup fails with "there is no parameter $1") and reads a composite constraint's columns in no particular order, so `outfit_garments_pkey` and `wardrobe_share_grantor_id_grantee_id_unique` show up as drift. The CLI (`drizzle-kit pull`) shares the unordered query: check column order in anything it emits. The `.dev.patch` suffix is what makes patch-package skip it under `npm ci --omit=dev` (the Docker runtime stage); a plain `.patch` for a devDependency errors there and only passes while `CI` is unset. Re-check both bugs before bumping drizzle-kit; a version bump drops the patch.
- **`pg` is pinned to the exact version `@mikro-orm/postgresql` pins** (8.20.0), so there is one node-postgres copy: the app's, and the legacy-database helper's (a devDependency now). Bump them together until the helper goes.
- **The drift check ignores one legacy statement.** `tablesFilter` hides `mikro_orm_migrations` from drizzle-kit but not its serial sequence, which introspects as a standalone sequence that push would drop; `test/support/schema-drift.ts` filters exactly that `DROP SEQUENCE`. `drizzle-kit pull` against a legacy database emits a `pgSequence` for it: delete it, never add it to the schema.
- **Drizzle writes a SQL field's columns without their table in a single-table select.** `db.select({ x: sql\`... ${other.col} = ${file.id} ...\` }).from(file)`renders`"col" = "id"`, so a correlated subquery compares the subquery table's own columns (`garment.photo_id = garment.id`) and silently answers wrong. `photoIsReferenced`is an uncorrelated`IN (... union all ...)`for that reason; in a`where` or a joined select the columns keep their tables.
- **Drizzle wraps a query builder embedded in `sql` in parentheses.** Around a select that is harmless (`with locked as materialized ((select ... for update))`); around an update, delete or insert it is a syntax error at `update`. A data-modifying CTE embeds the builder's `.getSQL()`, which is not wrapped (`lockForEdit`, `src/web/outfits/queries.ts`).
- **No `NULLS NOT DISTINCT`: drizzle-kit's introspection reads every unique constraint back as `nullsNotDistinct: false`**, so `unique().nullsNotDistinct()` is drift (drop and recreate) in `migrations.spec.ts` forever. Uniqueness over nullable columns is a unique index over their `coalesce`d values instead (`outfit_rule_owner_id_kind_a_b_unique`, #21); push compares an expression index without its expressions, so it reads back clean.
- **An index that mixes a column and an expression must write the column as an expression too.** drizzle-kit's introspection (the drift test's `pushSchema`) marks every column of an index with any expression as an expression, so `capsule_owner_id_lower_name_unique` declared with `table.ownerId` as a plain column beside `lower(name)` read back as drift (drop and recreate). It declares `owner_id` as the expression ``sql`${table.ownerId}` `` instead, which generates the same SQL.
- **drizzle-kit does not emit a type change on a column it renames.** `0001_calendar_day.sql` renames `date` to `day` and changes timestamptz to date; the generated file had only the rename, and the `ALTER COLUMN ... TYPE ... USING` was added by hand. The drift test catches a missing statement; the rename prompt needs a TTY (drive it from a terminal, not a pipe). Without one (an agent), as for `0003_user_device_push.sql`: write the SQL in drizzle-kit's form (`--> statement-breakpoint` between statements), build the snapshot with drizzle-kit's own `generateDrizzleJson(schema, previousSnapshotId)` from `drizzle-kit/api`, add the journal entry, and prove it with a second `npx drizzle-kit generate` ("No schema changes") plus the drift test. For `0004_garment_web.sql` (a rename among many other changes) drizzle-kit generated everything with the column still under its old name in the schema, then the rename, its `USING` and the data guards were written in and the snapshot rebuilt from the real schema.
- **A shipped migration gets no spec.** It is frozen (never edited or deleted, see Changing the schema), so a spec of its SQL cannot fail for a regression in our code; the proof of the schema is `test/integration/migrations.spec.ts` (drift against `src/db/schema.ts`, the index list) on the migrated template, and of the runner `migration-runner.spec.ts` (legacy detection, the lock, a fresh database). The per-migration specs and `migrateBefore` were retired on 2026-10-13 (git history: `test/integration/*-migration.spec.ts`, `test/support/migrate-before.ts`); a migration with a data fix is proved on a copy of production's rows by hand, in the PR.
- **Every migration starts with `SET LOCAL lock_timeout = '5s';`** (any positive value) (then a `--> statement-breakpoint`; 0051 is the model). The migrations share one transaction at boot, so without it a `pg_dump` or long reader makes the boot wait without limit instead of failing and retrying. `migration-lock-timeout.spec.ts` (unit tier) checks every file from 0051; 0000-0050 shipped before the rule.
- **A migration that changes data asserts its assumptions and aborts.** `0001_calendar_day.sql` raises (so the whole batch rolls back and the boot fails with `MigrationFailedError` naming the reason) if any calendar value is not UTC midnight or any row has notes, rather than shift a day or drop text. Do the same for any conversion whose correctness depends on what the data looks like.
