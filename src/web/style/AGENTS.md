# Style profile

`src/wardrobe/style.ts` (the value sets), `src/web/style/` (#34, slice 34a). How a person dresses and toward what: what Muse reads of their taste (`get_style_profile`, `src/web/mcp/tools/style.ts`), beside the feedback their decisions give it. **The user's own**: no route takes `?ownerId=`, shares never reach it (`authorization-account.spec.ts`). It outlived the wardrobe plans it was built with (#337).

- **Table** `style_profile` (one row per user, `drizzle/0016_wardrobe_plans.sql`): `styles` and `palette` as `text[]` sets (`storedSet`), the `budget` band, notes. Every value set is a check constraint from `style.ts` and `properties.ts`, as on `garment`, so a new style or band is a migration. **Not stored here**: the week's rhythm, derived from the week template (#16, `weeklyRhythm`, see Weekly auto-plan), and the home city, the weather's (`user_weather`, #14), which the page shows read-only (`homeNameSql`, with a link to Profile › Weather; nothing with `WEATHER_ENABLED` off) and never copies.
- **One writer**, `saveStyleProfile` (`queries.ts`, an upsert): the page's post and the seed. One reader, `styleProfileSql`, a scalar subquery so the page and `get_style_profile` read it with the week template in one statement (#251, #172).
- **Outfit rules** (#21; `docs/plans/2026-11-12-generator-rules.md`): table `outfit_rule` (`drizzle/0047_outfit-rules.sql`): `kind` (never | always) and per side exactly one matcher column set (`a_garment_id`, `a_category` (+ `a_type`), `a_color`, `a_pattern`; the same for `b`), each from its value set, stored once (`outfit_rule_owner_id_kind_a_b_unique` over the coalesced sides); a side's garment cascades. The model is `src/wardrobe/outfit-rules.ts`; the generator's reader, `outfitRulesSql`/`readOutfitRules` (`queries.ts`), rides in the generator's statement (Outfit gallery). Owner-only, like the profile: a grantee's ideas never read them (`styling-statements.spec.ts`, `garment-page.spec.ts`). 21c (the chips, `get_style_profile`) is next; its chip text is `ruleSentence` (`labels.ts`).
- **The page's Outfit rules section** (#21b, `outfit-rules.tsx`, `#outfit-rules`): the rules as sentences (`ruleSentence`: "Never {a} with {b}", "Always {b} with {a}"), each with Remove; the add form; then the gallery's avoided pairs (`avoidedPairsByNameSql`, Outfit gallery's), read-only but for "Allow again" (`POST /outfits/ideas/allow` with `returnTo`, back here). **Each side is one `<select>`**: categories with their types, colours, patterns, then the closet's garments, one option each, spelled only by `ruleSideValue` (`validation.ts`: `garment:<id>`, `category:<c>[:<type>]`, `color:<c>`, `pattern:<p>`) and accepted only as those by `OutfitRuleBody`, so a type outside its category is a 400 from the schema and `readRuleSide` maps an option to its `StoredMatcher` without checks of its own. Equal options are the same side ("Choose two different things."). **The one writer, `addOutfitRule(db, actor, rule)`**, is one statement (avoidPair's shape): a side's garment must be the actor's (owned now or once, locked `FOR SHARE`; else it throws `NotFound('garment')`, as `deleteOutfitRule` throws `NotFound('outfitRule')`: the routes refuse nothing themselves, guards.conf `[refusals]`), and a rule the owner has is `on conflict do nothing`, the page again (400) with "You have this rule already."; a never-rule's sides are put in one order first (`storedSides`, `src/wardrobe/outfit-rules.ts`: never is symmetric), so its mirror is that duplicate too, and its sentence may read the sides swapped from how they were typed (an always-rule keeps its order). **The accessory hint** under B is CSS alone (`group-has-[…]/rule`): shown for an always-rule whose B option carries `data-undrawn` (a category, type or garment outside `DRAWN_ROLES`), since the generator never draws one and the rule then holds only when it is locked.
- **Routes** (`routes.tsx`): `GET|POST /auth/profile/style`, a section of the Profile (`profile.EDIT_STYLE`), and the rules' `POST /auth/profile/style/rules` and `POST /auth/profile/style/rules/:id/delete` (another user's rule a 404, the writer's). Native posts (`PostForm`): the chips post only their own sets (anything else is a 400 from `StyleProfileBody`), `readStyleProfileForm` stores them in their set's order. Every write answers 303 to `styleSavedUrl(<flag>)` (`?saved=profile|rule-added|rule-removed|pair-allowed`, the rules' at `#outfit-rules`), whose toast `StripFlags` drops. The page is one statement after the session (`renderStylePage`: the profile, the week template, the home city, the rules with their garments, the form's garments, the avoided pairs), also for a refused rule's 400. A form cached before #16 still posting the week's `times-*`/`per-*` fields has them stripped by the schema, unread.
- **Specs**: `test/integration/style-profile.spec.ts` (the form, its sets, the rhythm, the home city with the weather on and off, the page's 2 statements; the rules added, refused, removed, the avoided pairs' undo); the owner-only rows are `authorization-account.routes.ts`'s.
- **Labels** (`labels.ts`): `style.style.<value>` and `style.budget.<band>`; `labels.spec.ts` fails on a value without one.
