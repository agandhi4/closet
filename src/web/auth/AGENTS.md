# Auth

- **Auth**: login is always required (the upstream `AUTH_ENABLED=false` mode was removed 2026-09-25). Ported to the web layer on 2026-09-26 (`src/web/auth/`, `src/web/sharing/`). JWT (HS256, `jsonwebtoken`, claims `userId`, `email`, `pwf`, 365 days) in an `access_token` cookie: httpOnly, `SameSite=Lax`, `Max-Age` 31536000 seconds (the token's own lifetime), never `Secure` (Conventions). bcrypt passwords. Emails are stored trimmed and lower case (`normalizeEmail`) and unique case-insensitively: the `user_lower_email_unique` index on `lower(email)`, which the lookups use. `drizzle/0005_email_lower_outfit_text.sql` normalized the older rows and aborts the boot, naming the user ids, if two would collide. Registration and update-email check the address inside their one write, with no lookup first (#171): `insertUser` is an insert-select `where not exists` (raw SQL: Drizzle's insert-select must list the serial id) and `updateEmail` an update `where not exists` another account with it, so a taken address returns no row and raises nothing (a unique violation is a Postgres ERROR whose DETAIL names the address). Only the race past that check hits the index; both catch `USER_EMAIL_UNIQUE` by name and answer it as taken, and rethrow any other violation. Registration hashes before it knows the address is taken, so a taken address costs what a free one does. The session is resolved once per request by `createSessionResolver` (`src/web/auth/session.ts`: cookie, JWT, user row, password fingerprint) into `req.auth` (`{ user: { id, email } }`, never the hash). Its one statement (`findSessionAccount`) reads the id, the email (the app bar's initial, the order mail's owner) and `right(password, 8)`, the fingerprint cut in SQL (`passwordFingerprintSql`, beside `passwordFingerprint` in `tokens.ts`; the request's own `pwf` is `sessionFingerprint(request)`), never the 60-character hash (#171), and, for a request whose `?ownerId=` names another user's wardrobe, that share's permission, which the access check then reads from the request (#170, see Sharing). Routes are gated by `requireSession`, which only reads `req.auth`: every route needs a session unless it says `config: { public: true }`; without one a page navigation is a 302 to `/auth/login` and an htmx fragment, a fetch or an outbox replay (`X-Closet-Queued`, which needs no Fetch Metadata: the HTTP twin sends none) a 401 with `HX-Redirect: /auth/login`. Handlers take the user as `sessionUserId(request)`. There is no password reset by email (removed with `src/email/` on 2026-09-25); a signed-in user changes it at `/auth/change-password`, which needs the current password, revokes every other session through the fingerprint and reissues this one's cookie. Changing the email (`/auth/update-email`) needs the current password too (checked before the address clash, so whether an address is taken is only told to the account's owner). **Step-up rule:** every route that changes or hands out a credential asks for the current password (change password, change email, delete account, creating a personal access token), so a borrowed unlocked phone or a stolen cookie cannot take the account or mint a credential that outlives signing out; each is `ACCOUNT_LIMIT`ed and says `config: { checksPassword: true }`: its session lookup reads the hash in the same statement, and the handler takes it from `sessionAccount(request)` (a `WeakMap` by request, never on `req.auth`, so no view or log line can reach it) instead of reading the row again. `sessionAccount` on any other route throws. `updatePasswordHash` is a transaction of two statements, in this order: the new hash (which takes the user's row lock), then the token and device revocations as data-modifying CTEs of one statement (`revokeAllTokensStatement`, both kinds, `revokeDevicesStatement`). **Never fold them back into one statement** (#171 did; #189 undid it): a statement's snapshot predates its lock wait, so a token minted while it waited survived the new password. `keep` names what of the changing device stays (`endpoint`, and `tokenId` for the API's change-password later). Deleting an account stays a transaction (rare, and the user's cascades are where its rows go). Routes that only narrow access (sign out, revoke an agent token or a device) do not ask: a deliberate exception, as minting stays password-gated. **Minting rechecks the password under the lock**: `createToken` takes `verifiedPassword`, the full hash the caller checked the password against (`sessionAccount`'s; #190's sign-in its own lookup's), and refuses `password-changed` if the row's differs once it holds the user's lock; Agent Access answers the form again asking for the current password. A push subscribe does the same under the lock against the session's fingerprint (#512, see Web Push). **Sign-in does the same work for an unknown email as for a wrong password**: the same lookup, a bcrypt comparison against the unknown-account hash of the configured cost (`configurePasswordHashing`, `PASSWORD_HASH_ROUNDS`: 12 in production, 4 in the test tiers; a constant per cost, since a hash made on first use cost the first unknown email after each boot twice the time), the same page; and `verifyPassword` marks its request, so every route that checks a password answers without Server-Timing (`markSecretChecked`, see Metrics). `auth.spec.ts` compares the two refusals. Signing out is `POST /auth/logout` (see Request security, Logout). **`Clear-Site-Data` is relayed to the landing page** (#244): WebKit applies it only to the response a load ends on, never a followed redirect, so the root onSend hook `createCacheClearRelay` (`session.ts`) sets a 60 s `cache_clear_pending` cookie (httpOnly, Lax, never Secure) on any non-document answer carrying the header (the sign-out, deletion and sign-in-over-another redirects, a revoked cookie's 302 or bodiless 401), and the next whole HTML document (any route: the login page, the profile, wherever `safeReturnTo` led) repeats the header once and clears the cookie. Fragments, redirects and static paths never consume it; a new way to end a session needs only `endSession`/`startSession`. A locked-out user's password is set by `npm run user:set-password -- <email>` (Deployment, Locked out). Wardrobe permissions come from one `resolveWardrobeAccess` (`src/web/sharing/access.ts`). The MCP endpoint takes personal access tokens instead of the cookie (see MCP server). `DISABLE_REGISTRATION` sends every registration route to the login page. See Architecture, Request security.

## Layout

`/auth/*`: the session resolver (`session.ts`, with `startSession`, `endSession` and the cache-clear relay), tokens, passwords, `requireSession` (`require-session.ts`) and `session-access.ts` (its decision), `login-path.ts` (`LOGIN_PATH`, which the service worker imports), `personal-tokens.ts` and `token-routes.tsx` (`/auth/tokens`: the MCP endpoint's tokens; `/auth/devices/:id/revoke`: Profile › Devices, the native clients' device tokens, #189; a revoke that finds nothing lands on its page with a notice, never an error page), `pages.tsx` (Profile, `/auth/profile`), `form.tsx` (`PostForm`, the only native-post form; disabled offline by default, its `form=` controls included, and `allowOffline="<reason>"` the only opt-out: guards.conf `@post-form-offline`, `expectFullPage`), `logout.tsx`.
