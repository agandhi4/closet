# JSON API

`/api/v1` (#190; the design is `docs/plans/2026-11-12-json-api.md`) is the native clients' JSON API. It is the third caller of the domain functions pages and MCP already call, never a backend of its own. The PWA never calls it: the server owns its HTML.

- **The surface** (`src/web/surface.ts`): `config.surface` is `page` (the default), `mcp` (`/mcp`) or `api`. The root onRoute hook `assignSurface` (`createApp`, before any route) stamps `api` on every route under `/api/v1`, HEAD twins included. A route that says otherwise, `surface: 'api'` outside it, or any other `/api` path (a `/api/v2`) stops the boot. `surfaceOf(request)` is the one reader. A request no `/api/v1` route matched counts as `api` by its path, in any case (`/api`, `/API/v1/me`; `isApiPath`, `src/web/api-path.ts`, the one rule, which the service worker's `bypassesWorker` reads too), so an unknown API path is a problem 404 that never reads the cookie. That covers the not-found handler and the static files' `GET /*` wildcard, which a GET matches before it falls to not-found. Readers: the root preValidation (no session, no page context), `requireSession`, the same-origin hook and the error handler.
- **The credential**: a `device` token in `Authorization: Bearer` (`createDeviceTokenHook`, `token-auth.ts`; `presentedBearer`, `src/web/auth/bearer.ts`, shared with `/mcp`). The scheme matches in any case. Two headers on the wire (a `rawHeaders` count) or two values folded into one are refused.
  - The cookie is never read on this surface, even one that carries a token.
  - An `mcp` token is the same 401 as an unknown one and records no use (#189).
  - Every refusal is one 401 `unauthorized`, `detail` "Sign in again…", with `WWW-Authenticate: Bearer realm="closet"`. To a client a 401 means one thing: sign in again.
  - A token in the query string is a 400 before anything reads it (`refuseQueryToken`): a key named `access_token` or `token` in any case, or any value holding `closet_`, repeated keys included. The value is never echoed. `loggableUrl` filters credential shapes on every surface (`scrubSecrets`).
  - Authentication happens once, at onRequest (after `refuseQueryToken`), before the body is read: an unauthenticated request is a 401 whatever its body (never a 400 or 413). A token revoked by another request mid-flight finishes that request; the next one is a 401 (the cookie's model).
- **Sign-in and sign-out** (`src/web/auth/api-routes.ts`, plan section 3):
  - `POST /api/v1/auth/token` takes `{ email, password, deviceName }` and answers 201 `{ token, tokenId }`, `Cache-Control: no-store`. It sets no cookie and is public.
    - It shares `checkSignIn` (`src/web/auth/sign-in.ts`) with the login page: `normalizeEmail`, then exactly one bcrypt comparison on every path, the unknown-account hash for an unknown email.
    - It mints through `createToken` with the hash it verified. A password changed (or an account deleted) under the lock is the same 401 "Incorrect email or password" as a wrong password, logged `password-changed`.
    - At the device cap the least recently used device is evicted, never an agent token (per kind, #189). The sign-in line names the evicted row.
  - `DELETE /api/v1/auth/token` revokes the calling token only, 204. It is 204 too when something revoked the token since the request authenticated, logged `(already revoked)`.
  - `GET /api/v1/me` returns `{ id, email, timeZone, today }`: `today` is `todayIn(APP_TIMEZONE)`, the day a wear or wash defaults to. It reads only the token's row.
  - No v1 route changes or hands out a credential behind a token (step-up, Auth). A future one takes `currentPassword` under `ACCOUNT_LIMIT`, and `updatePasswordHash`'s `keep.tokenId` keeps the calling device.
  - Once a token-authenticated route can mint, `createToken` needs an `excludeId`, so a device never evicts itself (decisions 2026-11-13, #189).
- **Limits**:
  - `SIGN_IN_LIMIT` is ONE checker for the login page and this sign-in (`signInLimit`, built in `webPlugin`), so an address gets 5 a minute in all and the 6th is a 429 at either door.
  - `SIGN_IN_ACCOUNT_LIMIT` (5 a minute per SHA-256 of the normalized email) caps guesses spread over addresses: the API door only.
  - `API_LIMIT` allows 120 a minute per token: one checker for the whole API, a preHandler after authentication. A route that serves private photo bytes sets `config: { apiPhotoBytes: true }` and counts on `API_PHOTO_LIMIT` (600 a minute per token) instead; the 401 is never counted on either.
  - `WEATHER_SEARCH_LIMIT` and `WEATHER_LOCATION_LIMIT` are shared with the page twins, one checker each in `weatherLimits` (`createWeatherLimits`, built in `webPlugin`): the weather search (page and API), the home write, the phone-location write and a trip's destination (page and API each), keyed by the token's user or the session's, so a user's two doors are 20 searches and 10 of each write a minute in all. A trip page's own search stays a route config (decisions 2026-11-13, #195a).
  - `LINK_IMPORT_LIMIT` is ONE checker for the page's link import, its photo choice and `POST /garments/link-imports` (`linkImportLimit`, built in `webPlugin`), counted after the wardrobe is judged and the cheap body checks pass (a refused body spends none, at either door).
  - A 429 is a problem with `Retry-After`.
- **Errors are RFC 9457 problem+json** (`src/web/problem.ts`'s `Problem`; `problemOf`/`sendProblem` in `errors.tsx`, the one module that may import `node:http`). The body is `{ type: "about:blank", title, status, detail, code, requestId }`, plus `errors: [{ path, message }]` for a schema validation.
  - `code` comes from `HttpError.code`. `NotFound`/`Forbidden` keep the page's message, which names no id.
  - A 500 has no `detail`. An unknown path's detail is "Not Found", never the URL.
  - A 503 `busy` (`OwnerLockTimeout`) carries `Retry-After`, as `HttpError.retryAfterSeconds` sets it.
  - A foreign Origin is a 403 problem (the same-origin hook). A missing Origin passes: no ambient credential rides here.
  - No CORS: no `Access-Control-*` header is ever sent, and a preflight is a problem 404.
- **The spec** (plan section 5):
  - `npm run api:spec` (`scripts/api-spec.ts`, the only importer of the devDependency `@fastify/swagger`) registers `apiPlugin` on a bare Fastify and writes `openapi.json` (OpenAPI 3.1). `info.version` is `v1`, never the sha.
  - `Problem` is one component (`addSchema`, named by its `$id`).
  - `GET /api/v1/openapi.json` (public) serves the committed file, imported, so tsc copies it into `dist/`.
  - `scripts/api-spec.spec.ts` (unit) fails when the committed file is not what the routes generate. It validates the document (`@seriousme/openapi-schema-validator`) and asserts every operation's declarations.
- **Logging** (logger `Api`): sign-ins with user, token row id and address; failures as user N or "an unknown email"; refused credentials with their reason and address; sign-outs. Never the token, the password or the device name. The `Http` access line on `api` and `mcp` carries `user_id` and `token_id` (the row id).
- **Resources** (`resource.ts`): `ListOf(item, { title, description, extra })` answers `{ data, pagination: { nextCursor?, limit } }` (plus `extra`, the grid's `total`); `ListLimit(featurePage)` caps at 100; `ListCursor` is the query's opaque cursor, `idCursor`/`readIdCursor` the id keyset (a forged one is a 400 `validation`); `offsetCursor`/`readOffsetCursor` a position, for an order no keyset holds (the trips); `literals(VALUES)` a stored enum; `withoutNulls(row)` drops null fields (required: Fastify serializes a null through a `string` schema as `""`). A feature's mappers and schemas sit beside it (`wardrobe/garment-resource.ts`). A form reader's refusal becomes the 400 through `refusedBody(errors, pointerOf)` (`refused-body.ts`: the garment, repair and trip forms).
- **A grantee's `?ownerId=`** share is read in the token's statement (`authenticateToken`'s `shareOf`, remembered as the session's is, #170) and `actorOf(request)` takes the token's user, so a feature guard (`garmentGuard`) works unchanged here and a grantee's read costs what the owner's does.

## Parity (#191)

A feature is done when its domain function has a page caller, an API caller, and an MCP caller where an agent needs it (plan section 5). `operations.ts` is the reviewed manifest; `test/integration/api-parity.spec.ts` holds the app to it.

- **`OPERATIONS`** lists every `/api/v1` operationId; `requireContract` refuses a route whose id is not there, so a twin names only a real operation.
- **`PAGE_WRITES`** classifies every page route that is not a GET (`METHOD /template`, every feature on; a POST that only renders too) as exactly one of `{ api: '<operationId>' }` (or a list, `Twin`, for a write of two shapes: `POST /calendar` plans, or with `replace` changes an entry; its matrix routes may reach either), `{ webOnly: '<reason>' }` (the plan's section 6 list; each reason a named constant, said once) or `{ pending: '#192'..'#195' }`. **`MCP_WRITES`** does the same for every tool with `writes: true` (`agentOnly` for Muse's round), listed but not required to have a twin.
- The spec fails on a route or tool nobody classified, a line whose route or tool is gone, and a twin no API route declares. An area PR that adds a twin turns its `pending` lines into `api` in the same change.
- **Refusal parity**: a matrix route (`authorization-<group>.routes.ts`) whose page route has a twin must carry `api: { ok, request }`, which must reach that operation. A read may carry one too (GETs are not classified): `GET /wardrobe` and `GET /wardrobe/:id` replay on `listGarments` and `getGarment`. `authorization-coverage.spec.ts` counts an `api` request as covering its API route, so an API id route needs a matrix twin or an EXEMPT line. Its group's matrix then replays every case on the twin with each actor's device token: the same outcome, `login` being the API's 401 (`docs/testing-integration.md`).

## Adding an API route

1. Add its operationId to `OPERATIONS` and turn its page twin's `pending` line into `api` (`operations.ts`). Write it in `src/web/<feature>/api-routes.ts`, a `FastifyPluginCallbackTypebox<ApiOptions>` registered in `apiPlugin`, calling the same domain function the page calls (parse, call, map). The user is `request.accessToken!.user.id`. A public route says `config: { public: true }` and `schema.security: []`.
2. Declare `operationId` (camelCase, unique), `tags`, a `summary`, the TypeBox `body`/`querystring`/`params` (a multipart route: `multipartBody`, below), and `response: apiResponses({ 200: Resource })`. Resource schemas carry `title` and `description`. Fastify serializes through them, so an unlisted column never leaves. `requireContract` refuses the route at boot without them.
3. A querystring is closed (#577): an undeclared parameter is a 400 `validation` whose `errors` name `querystring/<name>`, for every route with no per-route work (`validator.ts`: `declareQuerystring` gives a route without one an empty schema; the compiler sets `additionalProperties: false` and turns `removeAdditional` off). Declare every parameter the route accepts (`ownerId`, `v`), never loosen it; `api.spec.ts` sends a bogus one to every GET.
4. JSON is camelCase and leaves out nulls. A household day is `YYYY-MM-DD`, an instant ISO 8601 with `Z`, money a decimal string, and lists `{ data, pagination }` (plan section 2).
5. `npm run api:spec` and commit `src/web/api/openapi.json` in the same PR. Pin the route's statements in `api-statements.spec.ts`. Give each matrix route of its page twin an `api` request.

## Gotchas

- **Never pass a plugin's `prefix` on in its options.** Fastify hands a plugin's `prefix` option to every plugin registered with those options, which doubled `/api/v1` on the feature routes. `registerApi` puts the prefix on a scope around `apiPlugin` instead.
- **A `GET` under `/api` that no route matches reaches the static wildcard `GET /*` first**: `request.is404` is false there. That is why `surfaceOf` falls back by path, not by `is404`.
- **No coercion on /api bodies.** Fastify's ajv runs with `coerceTypes: 'array'`, which the pages need (forms post strings) and which corrupts JSON: a `0`, `""` or `false` met `{ type: 'null' }` as null (never-wash became the role's default) and `"3"` passed as 3. `apiPlugin` sets `jsonApiValidator` (`validator.ts`): bodies validate as sent, a wrong type is a 400 `validation`; querystring and params still coerce (`?limit=20`). So a nullable input is `Nullable(schema)`, a plain `anyOf` in any order. A `default` inside an `anyOf` (a maybe-empty body's field) is still refused at boot under strict mode: default in the handler (`?? 1`). A request schema `$ref` resolves only against the shared schemas `apiPlugin` itself adds (Problem); one a child scope adds fails the boot.
- **A body is closed only where its schema says `additionalProperties: false`** (#195c: the style profile and outfit rules): bodies compile with `removeAdditional: false`, so a closed one refuses an extra key as a 400 at `body/<key>` instead of stripping it (ajv strips inside an `anyOf` while trying branches). Every other body is open: closing one is a contract change (decisions 2026-11-13).
- **A multipart route declares `multipartBody`, never `body`.** Fastify would validate the unparsed body (undefined, as null) against a `body` schema; the handler reads the parts (`request.files({ limits })`) after the domain function has judged the garment, so a refused upload stores nothing. `multipartBody` (`contract.ts`) is for the spec only: `scripts/api-spec.ts`'s `transform` makes it the operation's `multipart/form-data` body.
- **A body schema that admits null is optional in the spec** (#546). @fastify/swagger marks every declared body required, but Fastify validates an absent body as null, so `Type.Union([Object, Null])` already accepts none: `markOptionalBodies` (`scripts/api-spec.ts`) sets `required: false` for those, and `api-spec.spec.ts` lists which.
- **`CloneType(schema, { description })` keeps the schema's own description** (TypeBox 0.34 spreads the options under it): it adds one to a bare schema (`IsoDateSchema`, `RowId`, `literals(...)`), never overrides one (`ListCursor`'s, a titled resource's). Say the rest on the route or the parent schema, and read the regenerated spec (#193c's review).
- **A route answering bytes** (a private photo) declares its 200 as `Type.Unsafe({ description, content: { 'image/webp': { schema: { type: 'string', format: 'binary' } } } })`: Fastify never serializes a stream, and the spec documents the media type. Its refusal is a problem like any other (`servePrivatePhoto`), never the page's bare 404. Its schemas are `private-photo-bytes.ts`'s (`PhotoBytes`, `PrivatePhotoParams`, `PrivatePhotoQuery`).
- **Hooks added in `apiPlugin`'s `onRoute` run after the root's**, the rate-limit plugin's included. So `API_LIMIT` is a `createRateLimit` checker in a scope hook, never a stamped `config.rateLimit`, which the plugin would never see.
