# Sharing (`/wardrobe-share/*`, the access resolver)

- **One resolver:** `resolveWardrobeAccess` / `authorizeWardrobe` (`access.ts`) decide whose wardrobe a request addresses (`?ownerId=`, `''` or absent for your own) and what the caller may do there (view, manage, own). Share-aware pages and MCP tools go through it (MCP via `wardrobeFor`, `mcp/tool.ts`); a route plugin binds `wardrobeGuard(db, <the resource an unseen wardrobe reads as>)` once (`garmentGuard` for the garment routes) and calls `authorize(request, need)`, which reads `?ownerId=` itself, so no route relays `request.query.ownerId` or re-declares the wrapper (2026-10-27); never re-derive access from `sessionUserId` plus a share lookup.
- **`Actor`** (#188): `{ userId, shareReadAhead? }`, what a domain function takes instead of a request; `actorOf(request)` (here: the session user and the share read ahead, so the statement counts hold) and `actorOf(ctx)` (`mcp/tool.ts`: the token's user). Refusals are `NotFound` / `Forbidden` (`src/web/refusals.ts`). `authorizeWardrobe(db, actor, ownerId, need, unseen)` takes an `Actor` (#188b) and throws them itself: `NotFound(unseen)` without a view, `Forbidden()` without the need; nothing in it sees a `FastifyRequest`.
- **The access check costs no round trip of its own** (#170): a request whose `?ownerId=` is a plain row id naming another user's wardrobe reads that share inside the session's statement (`shareToReadAhead` and `sharePermissionSql`, called by `findSessionAccount`; stored per request by `rememberShareReadAhead`, only for a cookie that opened a session). A page's actor (`actorOf(request)`, what `wardrobeGuard` builds) carries the share read ahead, which `authorizeWardrobe` uses when its owner id matches and otherwise reads the share itself (a body's `ownerId`, `?ownerId=05`, the MCP tools, whose actor has none). Nothing is cached past the request, so a revoked share stops access on the next one. An `/api/v1` request reads it the same way in the device token's statement (`authenticateToken`'s `shareOf`, `src/web/api/token-auth.ts`), and `actorOf(request)` takes the token's user there. Build the actor with `actorOf(request)`, never `{ userId: sessionUserId(request) }`: that still works but pays the lookup again. A repeated `?ownerId=` parses as an array: never read ahead, and a 400. **Layering**: `auth/queries.ts` imports `sharePermissionSql` from `sharing/access.ts`, and `sharing/access.ts` imports only `auth/require-session.ts` (`sessionUserId`) and `refusals.ts` of the web layer; `access.ts` must never import `auth/queries.ts` or `auth/session.ts`, or the modules form a cycle. `sharing-statements.spec.ts` pins each grantee page's count (the grid, garment page, wishlist and Styling 3, capsules 2) and the invite and Profile counts below.
- **Invites expire and are credentials** (#668): an unanswered invite lives `INVITE_LIFETIME_MS` (7 days) from `created_at`, derived, no column; `created_at` is stamped from the app's clock and every check compares it with `inviteCutoff(now)`, never Postgres `now()`, so the clock shift moves both. `acceptInvite` refuses `expired` on its read and carries the same cutoff in the write's `unanswered` guard (expired in between: `not-found`); `findInvite` returns `expired` (the landing says so, no Accept); `sharesOf` marks it (listed, no link, Revoke kept). An edit link asks for the password (Auth, step-up rule); `createInvite` is one insert-select under the grantor's row lock against the session's fingerprint (`upsertDevice`'s shape; `wardrobe_share` is not synced, so no owner lock), and a new password deletes the user's unanswered invites (`revokeOpenInvitesStatement`, in `updatePasswordHash`'s revocation statement). Accepted shares never expire. Fixtures that only need a share mint through `createInvite(db, id, role)` (no fingerprint): an edit link through the route needs the password and draws on `INVITE_LIMIT`.
- **Statements**: accepting an invite is a read (the invite with the share its grantor already gave the user, `existing`) and one write guarded by the token (`unanswered`: an invite answered meanwhile is "not found" and nothing changes), with no transaction; folding a second invite into an existing share is one statement (the delete and the upgrade as data-modifying CTEs). Decline and remove are one guarded `delete ... returning` each (the answerer is `coalesce(grantee_id, grantor_id)`); `removeShare(db, actor, id)` throws `NotFound('share')` for a share the actor is no party to (#188f). Profile › Sharing reads its three lists in one statement and sorts them in `sharesOf`. The invite landing (`findInvite`, public) reads the permission and the inviter's first name, never an email. Signed out it links to sign in and register with `returnTo` the invite (`invitePath`), and says what the invitee gets in their words with the first name (`sharedBy`), else "this wardrobe"; a successful Accept lands on the grantor's wardrobe (`wardrobeUrl(result.grantorId)`, the invite row's grantor), a refusal on Profile › Sharing (#661).
- **Which surfaces are share-aware** (take `?ownerId=` and serve a grantee): the wardrobe grid and garment pages (link import included), the wishlist, capsules, Styling, wears (owner only, but resolved through it), the MCP tools that address a wardrobe, and the changes feed's garments and capsules (every accepted share, through the cursor, never `?ownerId=`; `src/web/sync/AGENTS.md`).
- **Owner-only by design** (session user only, no `?ownerId=`): saved outfits (`/outfits`: every query scoped to the signed-in user, `?ownerId=` ignored), the style profile, the calendar (week and month), Ideas/gallery, insights and the year in review (`/wardrobe/recap`, #26: wear data never reaches a grantee, so `?ownerId=` is ignored and the menu offers it only on one's own wardrobe), trips, Today, the weekly auto-plan, selfies, saved looks (`/inspiration`, #22), sizes, and Profile. The wardrobe export (#200, `/wardrobe/export.*`) is owner-only too, but through the resolver: `?ownerId=` of a shared wardrobe is a 403 even for MANAGE, since it hands over the whole wardrobe with the owner's own records. They are one person's planning and history, and a grantee must never see them.
- **A new feature decides which list it joins, and says so here.** Don't copy a sibling's route shape without checking: a share-aware sibling routes through the resolver, and an owner-only one reads `sessionUserId` alone.
- **API** (#195c, `api-routes.ts`): only `GET /api/v1/shared-wardrobes` (`sharedWardrobesOf`, accepted shares, `ownerId`, `ownerFirstName` from `grantorFirstName`, never `grantorName`: no API answer carries an email). Invites, accept, decline and remove are web-only (`SHARING_ADMIN`, `operations.ts`; decisions 2026-11-13).
- **A public link is a state of the garment or outfit** (#669, decisions 2026-11-14): `shareable_id` is null until Share is tapped and null again after Stop sharing; `setPublicShare` (`share/queries.ts`) is the one writer for both, one UPDATE under the owner lock (`coalesce`, so racing taps answer one id; a Share after a Stop a new one). A garment's Share and Stop are owner and MANAGE (a grantee's link shows on the owner's page with Stop after the grant ends), an outfit's the owner's. `/share` and `/file/watermark/:id` (keyed by the item's id, never a photo's; `findPhotoByShareableId` repeats `findSharedOutfit`'s first-photo rule) are a 404 for anything not shared. No API twin yet (#959).
- Sharing's own pages live in Profile › Sharing (`/auth/profile#sharing`); `GET /wardrobe-share/manage` 301s there (R2 #82). The public share-link page is `share/`, not this directory.
