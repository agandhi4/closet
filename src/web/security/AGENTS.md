# Request security

- **CSRF**: `createSameOriginHook` (`src/web/security/same-origin.ts`) is a root `onRequest` hook added in `createApp()` before any route, so it runs before the body is read. A POST, PUT, PATCH or DELETE must name in `Origin` (or `Referer` when there is no Origin) either the origin it was sent to (`requestOrigin`, see Trusted proxies) or `SITE_URL`'s origin; anything else, no header included, is a 403. Tools send no Origin by default: the integration harness adds `Origin: http://localhost` by default (`sameOrigin: false` opts out), Playwright's `page.request` posts use `SAME_ORIGIN` / `signUpHeaders()` (`test/support/e2e-session.ts`), and the page audit (`scripts/audit/fixture.ts`) sets it. The cookie is also `SameSite=Lax`. Nothing changes state on a GET (signing out is a POST: a cross-site link could sign someone out). A bearer surface (`surfaceOf`, `src/web/surface.ts`: `/mcp`, and `/api`, an unmatched `/api` path included) is the one exception to "no header is a 403": the cookie is never read there, and pages cannot add `Authorization` cross-site without a (never answered) CORS preflight; a present foreign Origin is still a 403 (the MCP spec's DNS-rebinding rule), a problem body on `/api`. **The one page exemption is `config: { stateless: true }`**, allowed only on `STATELESS_ROUTES` (`same-origin.ts`; any other route saying it stops the boot, `assertStatelessRoute`, and `same-origin.spec.ts` pins the list): today only `POST /inspiration/share`, the manifest's share target when no service worker answered it, because Android's share post carries no Origin and must get a page, not a 403. A stateless route **writes nothing, reads only what it needs under a size cap and answers a redirect a cross-site page could link to anyway**; an absent Origin passes, a foreign one is still a 403 (`inspiration.spec.ts` proves it sends one SELECT and stores no file). Adding an entry is adding a CSRF exemption: review it as one.
- **Rate limits**: `@fastify/rate-limit`, registered at the root with `global: false` (`src/web/security/rate-limit.ts`); a route opts in with `config: { rateLimit: SIGN_IN_LIMIT }` (registration: 5 a minute per client address, before the body; the login page and the API's device sign-in count on ONE `SIGN_IN_LIMIT` checker, `signInLimit` from `webPlugin`, so 5 in all, the 6th a 429 at either door, and the API door adds `SIGN_IN_ACCOUNT_LIMIT`, 5 a minute per hashed email; `API_LIMIT`, 120 a minute per device token; `API_PHOTO_LIMIT`, 600 a minute per token for the routes marked `config: { apiPhotoBytes: true }`, the one way an API route serves private image bytes so a page of thumbnails never spends the JSON budget; see JSON API) or `ACCOUNT_LIMIT` (every route that checks the current password: 5 a minute per user, a preHandler after the session gate) or `LINK_IMPORT_LIMIT` (the link import, its photo choice and the API's link import: 10 a minute per user between them, one `createRateLimit` checker built in `webPlugin`, not route config, see Link import) or `WEATHER_SEARCH_LIMIT` (the weather's and a trip's city search: 20 a minute per user) or `WEATHER_LOCATION_LIMIT` (`POST /weather/home`, `/weather/here`, `/trips/:id/destination`: 10 a minute per user) or `VITALS_LIMIT` (`POST /metrics/vitals`: 30 batches a minute per user; see Metrics) or `CLIENT_ERROR_LIMIT` (`POST /errors/client`: 10 a minute per user; see Metrics, Error tracking) or `MCP_LIMIT` (`/mcp`: 120 a minute per personal access token, a preHandler after authentication); `HEALTH_LIMIT` is one `createRateLimit` checker for `/health/ready` and `/healthz` (60 a minute per client address; see Health). The MCP tool `add_garment_from_link` gets its own 10 a minute per user through `createRateLimit` (`MCP_LINK_IMPORT_LIMIT`), since it is a call to `/mcp`, not a route. Counters are in process memory, one per route config and one per `createRateLimit` call (a budget two routes share is one checker). A refusal is the 429 page (`tooManyAttempts` for a checker's). Tests give each sign-up its own `X-Forwarded-For` (`uniqueClient()` in the harness, `signUpHeaders()` for Playwright), which only works because 127.0.0.1 is a trusted proxy there.
- **Trusted proxies**: `request.ip`, `request.protocol` and `request.host` read `X-Forwarded-*` only from peers in `TRUSTED_PROXIES` (Fastify `trustProxy`). Behind Caddy it **must** include Caddy's address, or every visitor is Caddy's IP to the rate limiter and the same-origin check falls back to `SITE_URL`. Production's value does not yet cover Caddy: a homelab config change.
- **`/mcp` is public** through the `closet-mcp-gate` (`POST /mcp` only; `docs/operations.md`). The gate's address is inside `TRUSTED_PROXIES` (172.16.0.0/12), so `MCP_LIMIT` and refusal logging see the real client IP from `X-Forwarded-For`.
- **Refusals do not reveal ids**: what the requester cannot see does not exist for them, a 404 like an unknown id (an unshared wardrobe, a garment outside the addressed wardrobe, anyone else's outfit or entry, someone else's share); what they can see but may not change is a 403 (a VIEW grantee writing). `WardrobeAccess` (`src/web/sharing/access.ts`) documents it; `test/integration/authorization-*.spec.ts` is the matrix.
- **Public pages never show an email**: the share page (`/share`) and its Open Graph and Twitter tags say "Shared by" the owner's first name when set (`sharedBy`, `src/web/share/share-page.tsx`), else nothing; its query reads no email.
- **Outbound fetches (SSRF)**: the server sits on the homelab LAN beside the NAS, pgvault and the router, so a URL a user supplies is fetched only through `createOutboundFetcher` (`src/web/security/outbound-fetch.ts`): http(s) on the default port, no credentials in the URL; the name is resolved once and refused if any answer fails `isPublicAddress` (`public-address.ts`: private, loopback, link-local, multicast and reserved ranges, IPv6 outside 2000::/3, and IPv4-mapped, NAT64 and 6to4 forms judged by their IPv4); the fetcher then dials **the checked address** itself (`dial`, `outbound-dial.ts`, the one place a connection or an h2 session opens: guards.conf `@outbound-tls`, `@outbound-tcp`, `@outbound-http2`; net's `Socket` class is banned beside `connect`, #568), so nothing resolves the name again (DNS rebinding cannot swap it), while Host (h2's `:authority`), SNI and the certificate check (`rejectUnauthorized: true`, the system roots) keep the name; ALPN offers `h2` then `http/1.1` and anything but `h2` is HTTP/1.1 on the same socket, plain http always (#496b); one request per connection, a redirect a new dial and session, an h2 session destroyed (never closed) when its answer is done or its request fails before one, held to `HTTP2_LIMITS` (no push, 16 KB / 100 header pairs, 1 MB session memory) and its body refused unless it arrived whole (its content-length exactly, or with none a stream that closed cleanly, not by its session's death: `rstCode`, `wholeBody`; else `network`); a socket or TLS error is `network`, logged by its code alone; at most 3 redirects, each checked the same way; one 10 s timeout over the chain; the body is read only for a content type the caller accepts, and never past its cap in decoded bytes: an image past 15 MB is refused, a page past 2 MB is cut there (`truncated`: a product page's metadata comes first, #347); a user's URL answered 403, 429 or with a bot challenge header on any status (`cf-mitigated: challenge`, `x-amzn-waf-action: challenge`, AWS WAF's is a 202) is `blocked-by-site`, not `http-status` (a fetch naming `hosts` keeps `http-status`, its status its own); no cookies; one log line per fetch naming hosts only (links can carry tokens) and the last hop's protocol, `h2` or `http/1.1`, never ALPN's raw answer. A refusal is an `OutboundFetchError` whose `reason` names the rule. **A fixed third-party API** (Open-Meteo) uses the same fetcher: its requests name their `hosts` (the allow-list, checked every hop: a redirect elsewhere is `host-not-allowed` before it resolves) and accept `json` (512 KB cap); `createApp()` builds the weather its own instance. **A credential** (`authorization`) or a JSON body (`json`, a POST) is accepted only with `hosts` (else a thrown programming error), and such a request follows no redirect (a 3xx is an `http-status` refusal), so the credential reaches the named hosts alone: the order mail's JMAP client (`src/web/wardrobe/order-mail.md`) sends its Fastmail token so, through its own instance. `createApp()` builds the one fetcher of user URLs (logger `OutboundFetch`) and hands it to the web layer as `WebOptions.fetcher`; the per-user rate limit belongs on the calling route (`LINK_IMPORT_LIMIT`). The link import translates each `reason` (`REFUSALS`, `link-import/import.ts`), never naming a host or address. `test/integration/outbound-fetch.spec.ts` covers each rule on real sockets.
- **Redirect targets**: a user-supplied "go back here" value (`?returnTo=`) goes through `safeReturnTo` (`src/web/security/return-to.ts`): same-site paths only, anything else becomes the route's default. Never render or redirect to such a value without it.
- **Timing**: a function that checks a secret a request carries calls `markSecretChecked()`, and that request answers without `Server-Timing` (see Metrics).
- **Secrets in logs**: a route whose path carries a secret (the invite token) sets `config: { secretPath: true }`; every log line names requests through `loggableUrl()`, which then logs the route pattern, and otherwise filters credential shapes from the URL (`scrubSecrets`: a token a client put in a query string). Invite links are built on `requestOrigin`, not the raw Host, and reach their copy handler as a data attribute (`copyAndFlash`, `src/web/share/share-button.tsx`), never in script text.
- **A queued write's account** (#178a): a replay names the account that queued it (`X-Closet-Queued`); a root preHandler (`app.ts`) refuses one for another account than the session's, 409 `account`, before the handler writes (`src/web/offline-writes.ts`). Replays are same-origin fetches, so CSRF and the session gate apply unchanged (the gate answers one without a session the 401 by its header, never the navigation's 302); `Idempotency-Key` is logged sanitised and cut to 8 characters.
- **Logout**: `POST /auth/logout` (public, CSRF-checked like every POST) clears the cookie, sends `Clear-Site-Data: "cache"` (both through `endSession`, `src/web/auth/session.ts`, the one way a session ends on a device) and answers 303 to `/auth/login`; the service worker never relays it, nor any navigation post (#542: its fetch would carry this site's Origin, laundering a cross-site post past this check), and drops its session caches (pages and photos) when the page posts one of the four auth forms (`SESSION_ENDING`, `src/web/shell/session-caches.md`). The control is one native `PostForm` (`#logout-form`, `src/web/auth/logout.tsx`; disabled offline like every `PostForm`) in Profile › Sign out, the only place to sign out. `GET /auth/logout` signs nobody out: it shows a signed-in visitor a one-button "Sign out" page (old cached pages link there), anyone else the login page.
- **Session revocation**: a session token lives a year and carries `pwf`, the last 8 characters of the user's bcrypt hash. `createSessionResolver` compares it with the row on every request, so any new hash (change password, `user:set-password`; even the same password: bcrypt salts) ends every token issued before it. Signing out ends only this browser's cookie: a copied token stays valid until the password changes, the one server-side revocation (no session table). Rotating `ACCESS_TOKEN_SECRET` signs everyone out. A new password also revokes every personal access token of both kinds (agent and device) and every push subscription but the changing device's (`updatePasswordHash`, the one writer of a password: the hash, then the revocations, in one transaction behind the user's row lock, so a token minted or a device subscribed meanwhile is revoked too; see Auth and Web Push); rotating the secret touches neither (subscriptions go with `npm run push:revoke-all`, Deployment). **A revoked cookie clears its device**: when a request's session cookie no longer opens a session (fingerprint moved, user gone, bad signature, expired), `createSessionResolver` ends it on that reply with `endSession`: the cookie cleared and `Clear-Site-Data: "cache"`, on whatever route (public ones included) and whatever the gate answers (302, or 401 with `HX-Redirect` for htmx and `/selfies/*`), so the device's HTTP cache goes on its first request after revocation, logged (logger `Session`, `Rejected access token (<reason>): cookie cleared, Clear-Site-Data sent`). No cookie, no header: a first visit never gets it. The device that changed its password gets a new cookie and keeps its cache. `"cache"`, not `"storage"`: storage would unregister the service worker, empty its precache and drop the push subscription; the worker drops its own page cache (PWA, Page cache ownership) on `X-Session-Ended`, sent beside it (Chromium hides `Clear-Site-Data` from the response). `Clear-Site-Data` needs a secure context: the HTTP twin ignores it. `test/integration/session-revocation.spec.ts` covers each path and `test/session-revocation.spec.ts (retired 2026-10-13)` the browser's cache.
- **Signing in over a live session**: the login and registration forms stay open to a signed-in user, so B can sign in over A. `startSession` (`src/web/auth/session.ts`, both routes' one way to set the cookie) then sends `Clear-Site-Data: "cache"` beside B's cookie, so A's photos and selfies leave the HTTP cache; the same account signing in again keeps its cache, and a refused sign-in changes nothing. No `X-Session-Ended`: the worker drops its session caches as any sign-in form posts (`src/web/shell/session-caches.md`). `"cache"` leaves B's cookie alone. Safari/iOS honour it from 17, secure contexts only; elsewhere A's bytes stay behind unguessable URLs. `session-revocation.spec.ts` covers it.
- **The header reaches a document** (#244): WebKit ignores `Clear-Site-Data` on a redirect it follows, and every answer above is one (or a bodiless 401), so each also sets a 60 s marker cookie and the page it lands on repeats the header once (`createCacheClearRelay`, see Auth). It can only make a browser drop its own HTTP cache for this site, and only this server's answers set it (SameSite=Lax; the same-origin hook refuses a cross-site sign-out).
- **Private photo caching**: every photo a user owns is `Cache-Control: private` (never in a shared cache), keeping `max-age=31536000, immutable` for the `?v=` URLs: selfies (`PRIVATE_IMMUTABLE_YEAR`, `src/web/selfies/routes.ts`) and every `/file/**` variant (`PRIVATE_IMMUTABLE_YEAR` in `sendVariant`, `src/web/files/routes.ts`): public by unguessable name but still an account's wardrobe, and a share can end. Only the watermarked share preview (`/file/watermark/:id`, a day) is `public`: it is made for link-preview crawlers.

## Gotchas

- **All user-supplied URL fetches go through `outbound-fetch`.** Never `fetch()`, `http.get` or an HTTP library on a URL a user typed, pasted, shared or that a fetched page named: the production host reaches the NAS, pgvault and the router, and checking a name then making a normal request is open to DNS rebinding. `createOutboundFetcher` checks every resolved address and pins the connection to it. Its `destinations`, `resolve` and `tls` (the TLS fixture's trusted certificate, `test/support/tls-certificate.ts`) options are for specs only (`OutboundStandIn`); never `NODE_TLS_REJECT_UNAUTHORIZED`. The spec stands in for the internet with the loopback alias `127.0.0.2`, which Linux routes and macOS does not without `sudo ifconfig lo0 alias 127.0.0.2`.
- **What every request pays before its handler**: the timing context and the same-origin check at onRequest, the rate limiter only on opted-in routes (`global: false`), then at preValidation, off the static paths and the bearer surfaces, one HS256 verify and **one statement**, the session's user row by primary key: its id, email and the hash's fingerprint cut in SQL, not the hash (a `checksPassword` route reads the hash in the same statement, see Auth; a request whose `?ownerId=` names another user's wardrobe reads that share in it too, see Sharing); `requireSession` and the views read `req.auth`, never the row again. After it: Server-Timing, the security headers (a synchronous hook), compression, the histogram, the log line. A static path runs no statement. **Never cache the session's row in the process**: comparing its hash's fingerprint on every request _is_ the revocation, so a cache would keep a revoked cookie working.
- **The request log never holds a credential and skips static paths.** One line per request from the root onResponse hook (`GET /wardrobe 200 3.1ms`, logger `Http`, with `request_id`, `route`, `status`, `duration_ms`): method, `loggableUrl`, status, time, never headers. The session cookie is a year-long credential and logs reach `app.log` and Loki; the logger also redacts `cookie`, `authorization` and `set-cookie` under any logged `req`/`res` (`src/logger.spec.ts`). Fastify's own request logging stays off (`LogController({ disableRequestLogging: true })`): it would log every thumbnail and heartbeat.
