# Inspiration

`src/web/inspiration/` (#22; `docs/plans/2026-11-13-inspiration-library.md`): saved looks, the Outfits page's **Inspiration** tab (Saved, Ideas, Inspiration through `OutfitTabs`; `/inspiration` is the `outfits` section in `sections.ts`). A look is a photo, a link, or both, with a title and a note, and the pieces the owner reads in it (`inspiration_piece`, 22b); "Recreate this look" matches them to the closet (22b), saving the match as an outfit and "Find this" (22c), the share target, "Save as inspiration" and MCP (22d). **The owner's own, like the style profile**: `sessionUserId` alone, no `?ownerId=`; another user's look or photo is `NotFound('inspiration')` from the writers (a 404 like an unknown id), and nothing reaches a grantee, the share page or another user's MCP tools.

- **Tables** (`drizzle/0049_inspiration.sql`): `inspiration` (`owner_id`, `title`, `note`, `source_url` http(s) only, `photo_id` unique and nullable, `ON DELETE CASCADE` from `file`; `inspiration_photo_or_link_check`: at least one of the two), `inspiration_piece` (`(inspiration_id, position)` key, `role` from `INSPIRATION_PIECE_ROLES`, `type`, `colors[]` (at most `INSPIRATION_PIECE_MAX_COLORS`), `pattern`, all checked against `src/wardrobe/properties.ts`; `matched_garment_id` `ON DELETE SET NULL`: the garment chosen for the piece, a closet garment its outfit was saved with or the wishlist item "Find this" made, written only by the match view's two writes (22c); a piece's edit clears it). Positions are never renumbered: a removal leaves a gap, and a position is never reused: `inspiration.next_piece_position` (`drizzle/0050`) only grows, an add takes from it under the look's row lock (`takePiecePositions`), so a stale match view's post is a 409, never another piece's choice; at most `INSPIRATION_MAX_PIECES` (12, a 400 past it).
- **One writer** (`queries.ts`): `saveInspiration` (a new look; with a photo, its `file` row inserted `unwanted` in the same transaction: a look is a whole picture, so no cutout is ever queued), `saveInspirationWithPendingPhoto` (a pasted link's pending photo claimed with the look), `setInspirationPhoto` (locks the look, swaps the photo, deletes the replaced `file` row), `updateInspirationText`, `deleteInspiration` (the look then its `file` row). `writes.ts` holds the commit contract (Images): bytes stored before the transaction, deleted when it fails, unlinked after a commit that replaced or removed them.
- **Three ways in**: the add page's camera or library button (`POST /inspiration`, multipart, `photo-upload.tsx`) and a pasted link (`POST /inspiration/link`). The link goes through `importLink` (Link import: the outbound fetcher, its caps, `blocked-by-site`), under a `LINK_IMPORT_LIMIT` checker of its own; the photo it keeps as a pending photo is claimed in the look's transaction (`saveInspirationWithPendingPhoto`: `lockOwnerAndPhotoName`, `takePendingPhoto`, like a garment's save), and a page's `<title>`/product name becomes the look's title. A site that refuses us (a 502 of `REFUSALS`) or a page with no readable photo still saves the link, landing on its page with `?unread=<reason>` (a one-shot note: add a screenshot). A link the server never fetches (a 400 of `REFUSALS`) is the add page again with the reason, nothing saved.
- **The share target** (22d; `share-target.ts`, `share-confirm-page.tsx`, `public/js/share-confirm.js`, `src/web/shell/manifest.ts`; decisions 2026-11-13): a manifest has **one** `share_target`, so with `PWA_ENABLED` it is `POST /inspiration/share`, multipart (`photo`, `title`, `text`, `url`), for photos and links alike; without the worker it stays the link import's GET, links only. **A share never writes without a same-origin confirmation**: the service worker answers the POST navigation itself and **never sends it to the server** (`receiveShare`, the one navigation post the worker answers: `navigationPostAnswer`, Shell), because a cross-site page can auto-submit the same multipart form and the worker cannot tell it from Android's (no client id, no readable Origin): relaying it posted with our Origin and the cookie, a CSRF bypass. The first file declaring an `image/*` type is kept in Cache Storage (`shares-v1`, a session cache: one share at a time, a new one replacing it; at most `SHARE_PHOTO_MAX_BYTES`, 20 MB; gone after `SHARE_STASH_MAX_AGE_MS`, an hour) and the answer is a 303 to `GET /inspiration/share/confirm#<id>`, the id a fragment, so it never reaches the server or a log. That page (`FormPage`, no server state, its stash names in data attributes) has its module put the photo in a file input (`preparePhoto`), show it and enable **Save look**, a native multipart post to `POST /inspiration` like the add page's upload (same-origin, so the hook needs no exception; `fileSize` capped at `SHARE_PHOTO_MAX_BYTES`, a 413); the share's link (`linkIn`'s) and title are stashed beside the photo (`X-Shared-Url`, `X-Shared-Title`) and posted with it as `url` and `title` (`addUploadedInspiration`: a link not `^https?://` and parseable, a title past 255 or a field busboy cut is a 400, the stored bytes deleted). **Save look opens 800 ms after the preview decoded on a visible page** and refuses any click whose gesture began earlier (`public/js/click-gate.js`, `click-gate.spec.ts`), so a page cannot time a tap to its appearance; a share that cannot be read or decoded shows the missing state. Cancel deletes the share; Save only marks it in sessionStorage (`public/js/share-saved.js`) and **the look's page deletes it** (`forgetSavedShare`, inline in `show-page.tsx`), so a failed save keeps the photo for going back. **Without a controlling worker** (storage cleared, not yet installed) Android's post reaches `POST /inspiration/share` (`share-fallback.ts`), which **writes nothing**: a photo is a 303 to `confirm#not-opened` (open the app, share again; its bytes are never read), a link or text the same link page as the worker's (`linkPageFor`), nothing `#not-opened`; a body declared past `SHARE_BODY_MAX_BYTES` is a 413 unread. It is the same-origin hook's one `stateless` exemption (the OS's post has no Origin; see Request security); anything written there would be a CSRF hole. No photo is a 303 to `/wardrobe/new/from-link?url=<the link>` (`linkIn`, `link-text.ts`; or `?text=` cut to `LINK_INPUT_MAX`), which fetches nothing. A share while signed out lands on the login page and is lost (the sign-in drops the session caches, the stash with them); one while offline waits, the confirmation page (or the offline page at its address) reloading into it within the hour, Save disabled until the heartbeat answers. The same relay pattern on the auth posts is #542. Only a phone proves the share sheet.
- **"Save as inspiration"** on the link import page (`link-page.tsx`): a second submit button, `formaction` `POST /inspiration/link` (the paste), after Fetch so Enter still fetches; only on the person's own closet page (never `?to=wishlist` or a shared wardrobe's), since looks are their own.
- **Photos are private, like selfies**: served only to their owner by `GET /inspiration/photo/:fileName` and `/inspiration/photo/thumb/:fileName` (`sendPrivatePhoto`, `src/web/files/private-photo.ts`, shared with selfies: a bare 404 for anyone else, `private, immutable`), drawn through `inspirationPhotoUrl` (`PrivatePhoto`), never `imageUrl` (`photo-ref-guard.spec.ts` holds this directory to it). `publicPhoto` refuses their names on `/file/**`; `photoIsReferenced` counts `inspiration.photo_id`, so reconciliation never takes one for an orphan; account deletion takes them with the user's `file` rows. The service worker stores none (no image route matches `/inspiration/photo/`).
- **Pieces** (`piece-form.tsx`, `piece-input.ts`): one select names role and type together (`kind` = `role` or `role/type`, `PIECE_KINDS`, so a type is always its role's and nothing redraws on a role change), then a main colour, a second one and a pattern, each a select ('' none; `property.color.*` labels). A stored piece is an `AutosaveForm` posting to `POST /inspiration/:id/pieces/:position` (status line) beside its own Remove (`.../delete`); a new one is a native post to `POST /inspiration/:id/pieces`, both landing on `#look-pieces`. Anything off the form's options is a 400 (`PieceBody`). **Hints** (`piece-hints.ts`): the title (a pasted page's own until renamed) split where it lists garments and read by link import's `guessKind`/`guessColors`, one "+ Blazer · Blue" post each, never saved without the tap, none for a role and type the look already has.
- **Recreate this look** (`GET /inspiration/:id/recreate`, `recreate-page.tsx`): `recreateInputs` reads the look, its pieces, the owner's closet (`recreateInputsSql` in `src/web/gallery/queries.ts`: inCloset with `available` and the rest, the avoided pairs, the outfit rules) in **one statement after the session's**; `recreateLook` (`src/wardrobe/recreate.ts`, The garment model) ranks and re-picks. Each piece is a listbox `SnapStrip` (the chosen match centred, up to two alternates, then None), a missing piece says so, a re-picked one says the closest clashed, and `unfixed` pieces get one warning. The owner's closet only, never a grantee's. The look's pieces carry their `matched` garment in the same statement: `recreateLook` pins it (`saved`): while it still matches the piece it is that piece's chosen garment, always among its matches and offered to no other piece, so the defaults are unique; the save refuses (409) one garment posted for two pieces; and a piece whose match is on the wishlist takes no part in the `recreateLook` assignment (`recreateClosetPieces` in `recreation.ts`: it would reserve a garment a later piece needs) and shows "On your wishlist" with its item, no strip.
- **Save as outfit and Find this** (22c; `recreate-writes.ts`, `addPieceToWishlist` in `queries.ts`, `piece-wishlist.ts`): the match view is **one native `PostForm`** to `POST /inspiration/:id/recreate/outfit`; each strip posts a `position` hidden input, then its own `garment` (the strip's input, '' for None), pairs in document order (unequal counts, a piece twice: 400). "Find this" on a missing piece is a submit button of the same form with `formaction` (`POST /inspiration/:id/pieces/:position/find`; forms cannot nest), so the form has no text field: Enter never picks it as the default button. **`saveRecreation`** is one owner transaction: `lockLookForSave` (the look `FOR UPDATE`, then **its own statement** for the pieces' roles: one joined statement would read them as they were before a waited-for edit; every piece write, `updateInspirationPiece` included, takes the same `lockOwnLook` lock), `pickIdea` (closet garments only, top to toe, **once per garment set**, so a double tap answers `?alreadySaved=1`; named after the look's title, else as an idea), then `recordPieceChoices` (one `UPDATE ... FROM (VALUES ...)` storing a garment only if it is the owner's and of the piece's `pieceCategory`). A choice for a piece the look no longer has, or of another kind, is a 409 (`LOOK_CHANGED`) rolling back the outfit too; a garment gone from the closet is pickIdea's `garmentsGoneError`; all None is a 400. 10 statements with the session. **`addPieceToWishlist`** (in `queries.ts`: only queries open a transaction, `make guard-check`'s own-tx): the piece row `FOR UPDATE`, then (its own statement, so it sees what a waiting twin committed) whether its match is already an own wishlist item, answered without a write; else `insertGarment` with status `wishlist` (`wishlistFieldsOf`: the role's category, the type as its name and its presets, the colours, the pattern where the category takes one, a note naming the look and its link) and the piece pointed at it. 6 statements. **Not the look's link as the item's product link** (the plan said so): a lookbook page is not where the piece is sold, and two pieces of one look would be one product to Muse's never-again rule. "Save with wishlist pieces" (plan §4) is not built: the outfit holds closet garments only.
- **Pages**: the list (`list-page.tsx`, one statement after the session's, newest first; a tile is the thumb in a 4:5 frame or, for a link alone, its site), the add page (`new-page.tsx`, `FormPage`: the photo buttons above, the link field its one post), the look's page (`show-page.tsx`: the photo or the buttons to add one, Change photo, the link in a new tab, title and note in an `AutosaveForm`, Delete with a confirm). Every write is a native `PostForm`, disabled offline.
- **MCP** (`src/web/mcp/tools/inspiration.ts`; contracts in `tools.md`): `list_inspiration` (with `pieceCount`, the tagging queue), `get_inspiration` (`recreateOwnLook`, `recreation.ts`: the match view's own read and matching), `add_inspiration` (`addLinkedInspiration`, `MCP_LINK_IMPORT_LIMIT`), `set_inspiration_pieces` (`setInspirationPieces`: under `lockOwnLook`, a stored piece equal to one asked for is kept with its position and choice, the others removed, the rest added from the counter, so a position is never reused). The caller's own: no `ownerId`, a grantee's call is the 404.
- **Logs** (logger `Web`): `Inspiration <id> pieces set by user <id> (MCP): <n> kept, <n> removed, <n> added`, `Inspiration <id> saved as outfit <id> by user <id> with <n> garment(s)`, `... recreated by user <id>: its <n> garment(s) are already outfit <id>, nothing created`, `Inspiration <id> piece <n> added to the wishlist of user <id> as garment <id>`, `... already on the wishlist ... nothing created`, `Inspiration <id> piece <n> (<kind>) added|saved by user <id>`, `Inspiration <id> piece <n> removed by user <id>`, `Inspiration <id> saved by user <id> from an upload: <file>` (a share's Save too; the worker's console says `[sw] share target: <outcome>`, the page's `[share] ...`), `... from a link (<page|image>): <file>`, `... from a link without its photo (<reason>)`, `Inspiration <id> photo added|replaced ...`, `Inspiration <id> deleted by user <id> with its photo <file>`.
- **Specs**: `test/integration/inspiration.spec.ts` (add, list, the share's refusals, its confirmation page and the cap, "Save as inspiration", the link's outcomes, autosave, photo swap, delete, reconciliation, tagging and its 400s, the cap, the match view's one statement, the save and its refusals, Find this and its double tap), `src/wardrobe/recreate.spec.ts` (the matching), `piece-hints.spec.ts`, `mcp-inspiration.spec.ts` (the four tools, a grantee's 404), `src/web/shell/manifest.spec.ts` (the target), `share-target.spec.ts` (the worker's answer: stashed, too large, a link, never a fetch), the matrix rows in `authorization-outfits.routes.ts`, the pages in `pages.ts`.
