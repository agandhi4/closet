# The session caches: page cache ownership and the image cache (#121, #131, #226)

Linked from `AGENTS.md` in this directory (PWA and the service worker). Read it before touching what the worker stores for a signed-in account, or how it learns that the account changed.

**What a session owns.** `SESSION_CACHES` in `views/assets/src-sw.ts`: `pages-v2` (pages and fragments) and `images-v2` (`/file/**` `<img>` loads: photos, cutouts `/file/nobg/`, thumbs `/file/thumb/`, share previews). The cache holds one account's pages; no page or photo is ever served to a session it was not loaded for. Every session change goes through `dropSession` (or `emptySessionCaches` when the ownership lock is already held), which deletes every session cache, so a cache added to the list is dropped on every signal below. A new cache that holds anything an account's pages showed belongs in the list. `images-v1` (before 2026-09-28) outlived every sign-out and is retired on activate, like `pages-v1`. The `/file/**` photos are public and unguessable, but the cache is still the session's: on a shared device the next account must not be served the previous one's, offline included.

**Outfit selfies are never the worker's.** `/selfies/**` (their owner's alone, `src/web/selfies/AGENTS.md`) matches no image route, and a selfie (or any image, or a download) opened as a document is a page request whose answer is not HTML: `pageStore` stores only a rendered page (`isRenderedPage`, `page-cache.ts`). Before #226 such an answer, carrying no `X-Page-Account`, claimed the page cache for nobody (dropping the account's pages) and was kept there. The browser's HTTP cache holds selfies, emptied by `Clear-Site-Data: "cache"` when a session ends (`endSession`, and on Safari the page it lands on: below).

**How the worker learns the session changed.** It cannot read the httpOnly cookie, so:

1. Our sign-in, registration, sign-out and account deletion forms (`PostForm` `endsSession`, `data-ends-session`) tell the worker as the post leaves (`SESSION_ENDING`, from `public/js/pwa.js`; a page it does not control tells the registration's active worker), and it drops the session caches, held by `waitUntil` so the drop outlives the page. Whatever session the device had ends with each of these posts; one that then fails (a wrong password) costs a refetch. The post itself is the browser's (#542, below). `servedCopies` waits for the latest drop before reading the owner, so a copy matched while a drop runs is never served.
2. Every HTML answer names its account (`X-Page-Account`, the user id, set by `send()` in `src/web/render.ts`; absent signed out), and the worker drops the session caches before storing a page for an account other than the recorded owner (`claimPageCache`; the owner and the activation time are records in `pages-v2` under off-origin `page-cache.invalid` keys, so a drop takes them too).
3. A tab root whose revalidation comes back signed out or for another account drops them and reloads the page.
4. A page request whose followed redirect lands on the login page (`sentToLogin`, `page-cache.ts`: a boosted tap after the session was ended elsewhere, which no sign-out POST announced) claims the cache for nobody, dropping another account's pages and photos (a document load gets the same from the signed-out login page it stores, through (2)).

(1) covers every sign-in and sign-out made in the app, before the landing page is asked for: a sign-in lands on Profile, which is fetched first, never from the cache (`page-cache.spec.ts`), and its answer for the new account claims the cache (2). (2) and (3) are the backstop for a session change the worker never heard of (a spec's `page.request`, a page that loaded without `pwa.js`): the first page of the new session empties the caches, and at worst a tab root opened straight after shows the old copy until its revalidation lands and reloads it. The push subscription goes with a sign-out or deletion on the signed-out login page it lands on (`<push-signed-out>`); the outbox's records through the page's own drain-and-discard and (2)'s claim (`outbox.md`).

**The worker never answers a navigation post** (#542; until then `sessionBoundaryHandler` relayed the four auth posts). A fetch listener above every route stops the fetch event of any navigation that is not a GET (`navigationPostAnswer`, `page-cache.ts`), so the browser posts it as it is (the share target alone is answered on the device, a stash and a 303 with no fetch) and the server's same-origin check judges its real Origin. The worker cannot tell our page's post from a cross-site page's auto-submitted form (it sees neither `Origin` nor `Sec-Fetch-*`, and `referrer` can be stripped), and its own fetch in the post's place made the worker the request's client: this site's Origin, the Lax cookie, accepted, which let any site sign a victim into the attacker's account or sign them out. Only our own pages can message the worker, so what it must learn about a post comes as (1)'s message. The relay existed for #239: WebKit never settles a fetch whose opaque redirect carries `Clear-Site-Data` (`NetworkResourceLoader::didFinishWithRedirectResponse`), so the worker followed the redirect itself and answered `Response.redirect(landing, 303)`. A navigation the worker leaves alone is the browser's own load, which follows the 303 like any Safari tab, so the hang cannot happen; GET navigations go through the navigation preload, which settles on such a redirect in WebKit too (a revoked cookie's 303). What the relay also covered and is gone: a sign-out whose answer was lost after the server acted (the drop now comes before the post, so it is covered), a refusal saying `X-Session-Ended` (a wrong password over a cookie revoked elsewhere: the next page's claim drops the caches), and the offline page for a post that raced a lost connection (the browser's error page now; every `PostForm` but the queued ones is disabled offline).

**Generations** (#121, #226). Every drop starts a new one; a page or image request records the one it started in (`handlerWillStart` of `pageStore` and `imageStore`), and its answer is stored, or claims the cache, only while that is still current. For pages it is checked in `claimPageCache` under the lock that serializes claims and drops. Without it a slow page for A that landed after signing out and in as B reclaimed the cache for A (offline, where no later page puts it right, B then opened A's wardrobe); a slow photo stored A's image into B's cache. In memory on purpose: a stopped worker has no requests in flight. Workbox writes after `cacheWillUpdate`, so a drop can still fall between the two: `ownedCopies` reads a page back only for the account that owns the cache, and `imageStore`'s `cacheDidUpdate` deletes a photo whose generation ended meanwhile (either it sees the new generation, or the write finished before the drop, which deletes it with the cache).

**The offline warm** (#286, `offline-warm.md`) writes only through these rules: it claims the caches for the warm list's account (`X-Page-Account` on `GET /offline/warm`) before fetching, every page and thumb goes through `pageStore`/`imageStore` **stamped with the run's generation** (`runOf`, `generationFor`), so a drop mid-warm refuses what was in flight and anything started after it, and the run stops at the drop; its `warmed-at` record lives in `pages-v2` and goes with it. A warm's fetches are not navigations: a session gone answers them 401 (never `sentToLogin`'s redirect), and a revoked cookie's `X-Session-Ended` reaches no page's claim, so the warm reads both itself and drops the session (`endFetchedSession`). The offline page in `pages-v2` is stored without the expiration (`offlinePage`), so no warm evicts it.

**The outbox's store** (#178, `outbox.md`, The worker's part) is not a cache but follows the same boundaries: a claim for a new owner (`claimForAccount`, run by the next page of another account) deletes every other account's queued writes unsent. The worker no longer sees a sign-out or an account deletion (SESSION_ENDING drops only its caches), so leftovers wait for that claim, and a sign-out asks before discarding them (`outbox.md`); a revoked session keeps them for a sign-in as the same account. A sync's refetch (`OUTBOX_SYNCED`) and the activation refresh (`updates.md`) write only through `pageWarmer`, stamped with their run's generation (`runOf`), like a warm; an older build's copy is still read back only for the owner (`servedCopies`).

**Not the worker's to clear.** The browser's HTTP cache holds `/file/**` photos (`public, immutable`) and selfies (`private, immutable`) as well. A sign-out, an account deletion and a revoked cookie empty it (`Clear-Site-Data`), in Chromium; WebKit's source applies the header only to a response the load ends on (`NetworkResourceLoader::didReceiveResponse`), never to a redirect it follows, and every one of these is a 303 or 302 (before #239 the worker's opaque fetch of the sign-out applied it, and hung). So the server repeats it on the page the redirect lands on (#244, `createCacheClearRelay`, `src/web/auth/AGENTS.md`), the browser's own load of it in the installed app as in a tab (#542: the worker no longer fetches the landing itself). A sign-in over a live session sends it the same way. `pageStore` deletes `Clear-Site-Data` from every copy it stores (WebKit and Firefox show the header; Chromium hides it), so no cached page replays a clear.

**Not instant everywhere: the rollout window.** The worker never calls `skipWaiting()` (the policy is never to force a reload; see Updates in `AGENTS.md`), so after a deploy with a change here, a device with the app still open keeps running the old worker until the user taps Reload on the update toast or every tab of the app closes. Until then it has the old worker's rules: for #226, `images-v1` kept and not dropped on a session change, and selfies opened as a document stored in the page cache. The new worker retires `images-v1` on activate (`RETIRED_CACHES`), so the leak ends there. A fix to these caches cannot reach an open tab sooner.
