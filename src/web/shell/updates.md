# Updates: activation, the activation refresh and each build's static files (#180, #656)

Linked from `AGENTS.md` in this directory (PWA and the service worker). Read it before touching the update toast, what a new worker does with the pages an older one stored, or the per-build static cache (`assets-v2`).

**The toast.** The worker never calls `skipWaiting()` on install. `pwa.js` shows "Update available: Reload" on `waiting`, posts `SKIP_WAITING` on tap and reloads on `controlling`. Reload needs the server: while `<html data-connectivity>` (the heartbeat, never `navigator.onLine`) is not online it is disabled and the toast says "reload once you're back online", re-enabled on `connectivity:change`. Only the waiting worker's toast is guarded: another window of the app is claimed by the new worker without reloading (clientsClaim) and keeps its toast, whose Reload then only reloads; pwa.js keeps the update's state itself (none, waiting, active), not Workbox's `isUpdate`, which is false in a page opened before the first worker (#180).

**Why not defer the activation** until the new build's copies are ready: the waiting worker would have to fetch every page into a staging cache, a second session cache (generations, owner claims, drops, twice the storage), whose copies are days stale by the time the user taps Reload. The tap reloads at once; the refresh happens after it.

**Older-build pages are kept, not deleted** (#656). Every copy stamped before `activated-at` (a record in `pages-v2`) was rendered by an older build. Until 2026-11-13 `servedCopies` deleted each on read, so after every deploy the phone showed the offline page where yesterday's wardrobe was. Now such a copy is served by NetworkFirst's offline fallback with its age (freshness.js reads its stamp as for any copy), never opened stale-first (`StaleTabRoot`): online the server's page answers.

**The activation refresh** (`refreshOlderBuildPages`, `src-sw.ts`). Each `WARM_PAGES` (pwa.js posts it on every signed-in load, on `controllerchange`, on visible and on back online) first fetches again every page and `|hx` fragment the cache holds from before `activated-at`, one at a time in `cache.keys()` order, then runs the daily warm (`offline-warm.md`) only if the refresh completed. Not from the `activate` event: its `waitUntil` would hold the activation, and every navigation waiting on it, for the whole refetch. The cache is the to-do list, so a run cut short resumes at the next `WARM_PAGES` with what is left, and a second deploy makes the new copies due again; `refreshed-at` (later than `activated-at`: nothing due) spares a load the scan. Its own generation (`runOf`); a missing or signed-out owner means nothing to refresh. Each key is asked as it was stored (`refetchCachedPage`, shared with a sync's refetch, `outbox.md`): `HX-Request` for a `|hx` key, `X-Closet-Warm`, through `pageWarmer`'s plugins (the offline page through its own rules, outside the expiration). The answer table is `refetchVerdict` (`page-cache.ts`, unit-tested): 200 stored; 404 and 403 delete the copies; a redirect to another page is not stored and the old copy stays; 429 and 5xx stop the run, copies kept; a 401, `X-Session-Ended` or a redirect to the login page drop the session caches (`endFetchedSession`). That last is deliberate: it is how a password change or a revocation reaches a lost phone, and the cost is that an expired cookie meeting a deploy loses the offline copies. Offline, the first fetch fails and the run stops quietly, copies untouched. It replaces existing keys only, so it reads no storage budget (the warm after it does).

**Each build's static files** (`assets-v2`, `src/asset-cache.ts`). An older build's page offline must meet its own build's scripts: its importmap names that build's modules, and B's module importing a name A's importmap lacks fails the whole module graph (no freshness label, no outbox); Tailwind classes only A used are missing from B's `bundle.css`. The precache holds only the active build's bytes (Workbox deletes the previous revisions on activate) and ignores `?v`. So a route ahead of `precacheAndRoute` answers every first-party `?v=` URL under `/js/`, `/vendor/`, `/modules/` and `bundle.css` by its exact URL from `assets-v2`; without an exact copy it serves the precache's bytes (never kept under the URL) and fetches the network's behind it, kept only when the server's `X-Asset-Version` (`src/static-assets.ts`) is the build the URL names (`answersItsBuild`): the server ignores `?v` and can be a deploy ahead of the worker. Builds are kept whole, the newest two (`keptBuilds`; a builds record in the cache, newest first), never evicted per file. Unversioned files (the content-hashed fonts) stay the precache's. Not covered: a build's files it never stored under this rule (the first deploy carrying it, or a page of a build two deploys back) are this build's bytes, as before.

**Specs.** `test/sw-update.spec.ts` (390 px): the toast, Reload disabled offline, one reload onto the new build; then a page cached under build A opens offline under B with its age and no page error; the refresh walks the due keys in order, stops at a cut key and resumes there, each key answered once (counting only `X-Closet-Warm` requests). `src/web/page-cache.spec.ts` (`refetchVerdict`), `src/asset-cache.spec.ts` (the store and keep rules), `test/integration/delivery.spec.ts` (the header).
