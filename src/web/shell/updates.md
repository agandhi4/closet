# Updates: activation, the activation refresh and each build's static files (#180, #656)

Linked from `AGENTS.md` in this directory (PWA and the service worker). Read it before touching the update toast, what a new worker does with the pages an older one stored, or the per-build precaches (`closet-precache-<id>`).

**The toast.** The worker never calls `skipWaiting()` on install. `pwa.js` shows "Update available: Reload" on `waiting`, posts `SKIP_WAITING` on tap and reloads on `controlling`. Reload needs the server: while `<html data-connectivity>` (the heartbeat, never `navigator.onLine`) is not online it is disabled and the toast says "reload once you're back online", re-enabled on `connectivity:change`. Only the waiting worker's toast is guarded: another window of the app is claimed by the new worker without reloading (clientsClaim) and keeps its toast, whose Reload then only reloads; pwa.js keeps the update's state itself (none, waiting, active), not Workbox's `isUpdate`, which is false in a page opened before the first worker (#180).

**Why not defer the activation** until the new build's copies are ready: the waiting worker would have to fetch every page into a staging cache, a second session cache (generations, owner claims, drops, twice the storage), whose copies are days stale by the time the user taps Reload. The tap reloads at once; the refresh happens after it.

**Older-build pages are kept, not deleted** (#656). Every copy stamped before `activated-at` (a record in `pages-v2`) was rendered by an older build. Until 2026-11-13 `servedCopies` deleted each on read, so after every deploy the phone showed the offline page where yesterday's wardrobe was. Now such a copy is served by NetworkFirst's offline fallback with its age (freshness.js reads its stamp as for any copy), never opened stale-first (`StaleTabRoot`): online the server's page answers.

**The activation refresh** (`refreshOlderBuildPages`, `src-sw.ts`). Each `WARM_PAGES` (pwa.js posts it on every signed-in load, on `controllerchange`, on visible and on back online) first fetches again every page and `|hx` fragment the cache holds from before `activated-at`, one at a time in `cache.keys()` order, then runs the daily warm (`offline-warm.md`) once the refresh asked every key (failed ones included: one bad page never holds the warm back). Not from the `activate` event: its `waitUntil` would hold the activation, and every navigation waiting on it, for the whole refetch. The cache is the to-do list, so a run cut short resumes at the next `WARM_PAGES` with what is left, and a second deploy makes the new copies due again; `refreshed-at` (later than `activated-at` and before its `retryAt`: nothing due) spares a load the scan. A key that failed backs off (#782, `RefreshBackoff`, `page-cache.ts`): a record beside it in `pages-v2` (`refresh-backoff?key=`) says when it is asked again, 5 min doubling to a day, reset by any other answer and by a later activation (each record names the `activated-at` that wrote it: a deploy may have fixed the page); runs before then pass it over unasked, and `refreshed-at` is written once every key was asked or is backing off, with the earliest backoff's end as its `retryAt`, so a failing page is still asked again, but not on every load. Its own generation (`runOf`); a missing or signed-out owner means nothing to refresh. Each key is asked as it was stored (`refetchCachedPage`, shared with a sync's refetch, `outbox.md`): `HX-Request` for a `|hx` key, `X-Closet-Warm`, through `pageWarmer`'s plugins (the offline page through its own rules, outside the expiration). The walk is `refetchInTurn` and the answer table `refetchVerdict` (`page-cache.ts`, unit-tested): 200 stored; 404 and 403 delete the copies; a redirect to another page is not stored and the old copy stays; any other 5xx (this page failing) is counted and passed over, its copy kept and due again; only signs the server is unreachable or throttling stop the run, copies kept (a thrown fetch, 429, 502, 503, 504); a 401, `X-Session-Ended` or a redirect to the login page drop the session caches (`endFetchedSession`). That last is deliberate: it is how a password change or a revocation reaches a lost phone, and the cost is that an expired cookie meeting a deploy loses the offline copies. Offline, the first fetch fails and the run stops quietly, copies untouched. It replaces existing keys only, so it reads no storage budget (the warm after it does).

**Each build's static files** (`src/static-build.ts`, docs/decisions.md 2026-11-13). An older build's page offline must meet its own build's scripts: its importmap names that build's modules, and B's module importing a name A's importmap lacks fails the whole module graph (no freshness label, no outbox); Tailwind classes only A used are missing from B's `bundle.css`.

- **The key is the content.** `?v=` is, in production, `staticBuildId` of the precache manifest: `scripts/generate-sw.ts` writes it into `public/build.json` with the `sw.js` it injects, and the worker computes it from its own manifest, so a page names the precache holding exactly its bytes. A deploy that changes only server code keeps every `?v=` (no new worker installs then). Dev and the integration tier key by the release instead (`BuildInfoOptions.trustStaticId`): a lingering build.json never names what they serve. The release itself (health, /about, Sentry) is unchanged.
- **One precache per build** (`closet-precache-<id>`, a `PrecacheController` the worker drives itself). The manifest is the whole `?v=` set: `/modules/` and `js/errors.js` are precached too (the build fails without them: `MUST_PRECACHE`), since the warm stores pages as HTML without their subresources. Workbox's install fails if any entry fails; `installPrecache` then checks every key is in the cache (another activation's cleanup can delete it mid-install) before `installed-at`. No cross-worker record: each marker is written once, into its own build's cache.
- **Serving**: a route ahead of the precache's answers every first-party `?v=X` URL from X's precache only (`answerVersionedAsset`, `ignoreSearch` over Workbox's revision key); without one, the network, stored nowhere. The content-hashed fonts (`/vendor/fonts/`, no `?v=`) come from the worker's own precache, else the kept older build's (`answerContentHashed`, #780): an older page's bundle.css names its own fonts, and one name is one set of bytes. Every other precached file is the worker's own; one a page names with `?v=` outside the versioned roots (`/favicon.ico?v=`) matches without it (`unversionedPrecacheVariants`, the PrecacheRoute's `urlManipulation`, #781), never a versioned root's.
- **Cleanup**: on activate, before writing its own `activated-at`, the worker keeps its precache and the latest other to have activated (the one it replaces), and drops the rest (`dropOtherPrecaches`): two deploys before Reload keep the active build, the skipped one goes. Workbox's default precache, `assets-v1` and its own per-entry cleanup are gone.
- **The fallback**: every rendered page names its build (`X-Asset-Version`, `send()` in `src/web/render.ts`). A copy of any build but the worker's own (an older one, or a newer one the server rendered before its worker installed) is served only while that build's precache is installed (`meetsItsBuild`); otherwise (dropped by a later activation, not installed yet, or a copy from before pages named their build: the first deploy carrying this) `servedCopies` deletes it on read, as before #656, and the offline page answers.
