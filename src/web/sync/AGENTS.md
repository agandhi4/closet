# The changes feed

`GET /api/v1/changes?cursor=&limit=` (#196b; `listChanges`): a native client's sync, every synced row and deletion after its cursor, across the caller's own wardrobe and each one shared with them. No page twin: the PWA reads pages. The rows are stamped by the sync triggers (`src/db/AGENTS.md`, The sync triggers); the plan is PR #605.

- **Files**: `feed.ts` (`readChanges`, the registry `FEED`), `cursor.ts` (the position, its encoding, `isExpired`), `queries.ts` (the wardrobes read, the keyset read), `api-routes.ts`.
- **One `REPEATABLE READ READ ONLY` transaction per page**: the wardrobes (self, then each accepted share by owner id, `acceptedSharesWith`) with `revision` and `sync_floor`, then one keyset `union all` (a branch per resource and one for `sync_tombstone`, per wardrobe, each on its `(owner, revision)` index), then one batched read per resource on the page. 6 statements for a page of garments at any `limit`, 14 for a page of the nine resources its fixture writes (a read each), 5 for an empty page (`api-statements.spec.ts`). Never a per-row read.
- **Order within a wardrobe: `(revision, kind, resource, id, seq)`**: kind 0 a deletion, 1 a row (a revision's deletions first); `resource` the table, compared `COLLATE "C"` on both sides; `seq` the tombstone's id (0 for a row). A page fills one wardrobe before the next. Positions only move forward; a row rewritten between pages gets a higher revision and comes again (a resend, never a skip).
- **The end is exclusive** (`endOf`, kind 2): a finished wardrobe resumes after the snapshot's `user.revision`, so a wardrobe still at the backfill's 0 is not resent forever. The end comes from the snapshot, never the highest row seen: a revision commits with its rows under the owner lock, so nothing at or below it is in flight.
- **Expiry** (`isExpired`): a position before the end of `sync_floor`'s deletions is a 410 `cursor_expired` (full sync), unless its pass began at or above the floor (`Position.floor`: a full sync paging through rows below the floor must not restart forever). A fresh read leaves out tombstones at or below the floor. So does a cursor answered when `SYNC_ROOTS` was shorter (`FEED_COVERAGE`, a bit per root): it never saw the new roots' older rows. #608 moved it once: every device re-syncs in full after that deploy (intended).
- **A full sync is self-describing** (`snapshot`): every page of a sync begun without a cursor carries `snapshot: { wardrobes }` (the caller's own, then each accepted share), held across pages by the cursor's `s: 1` until the page where `more` is false. After that page the client drops every synced row not re-sent and every wardrobe not listed, since the fresh read sends no deletions at or below the floor and no `revokedWardrobes`. A 410 mid-way restarts it from no cursor.
- **A grantee's wardrobe** carries only `shared` entries (garments, every status, and capsules), its garments in the grantee shape (no `care`, no `repairs`: `garmentsByIds` reads the log only where the viewer owns it). A cursor naming an owner the caller no longer sees drops it and lists it in `revokedWardrobes`. `?ownerId=` is a 400 (the closed query).
- **A feed shape is the API resource minus what tables that never move its revision derive** (decisions 2026-11-13); the client derives those from the feed's other resources. Per resource (`Synced…` beside its API resource):
  - `garment`: no `worn`, `wornSinceWash`, `lastWorn`, `cost`, `costPerWear`, `capsules` (wears, capsules).
  - `outfit`: `slots` (category, `garmentId`) for `garments` and `toBuy` (the garments'); no proposal `agent` (the token's name), `planned` or `worn` (the entries'). Muse's proposals are in it, with their reaction (decided on #607).
  - `calendarEntry`: `outfitId` for `outfit` (its name and garments); no `selfieId`/`selfiePhoto` (the `selfie` names its entry).
  - `trip`: its stored fields, `outfits` flat (for `days`/`anyDay`), `extras`, `packedGarmentIds` (stale marks included: the reads ignore them); no `phase` (the day's), outfit garments, `wornTodayEntryId` (the calendar's) or `packing`, derived from the outfits' slots and garments.
  - `weekPlan` (no API resource): `createdAt`, `entries` (`entryId`, `outfitCreated`); not the planner's targets, the re-plan's own input.
  - `selfie`, `brandSize`, `styleProfile`, `measurements`: nothing dropped. The last two are one row per user, the change's `id` the user's. Outfit rules and the week template are not synced roots, so not in the feed.
- **Adding a resource**: a new `SYNC_ROOTS` table fails tsc until `FEED` has its entry (a `Record` of `SyncResource`): its API `name`, `shared` (`feed.spec.ts` holds it to garments and capsules, the share-aware list), its titled feed schema beside its API resource, and a batched `…ByIds(db, ids)` reader beside its per-id one, one statement for any owners, in its feature's `queries.ts`. Regenerate `openapi.json`, extend `api-changes.spec.ts` and the statements pin.
- **Tests**: `test/integration/api-changes.spec.ts` (the delta across pages, a page boundary inside one revision, the backfill, a held writer, the floor, a full sync's snapshot, a grantee's feed; per owner resource group its delta, a child write resending its parent); `feed.spec.ts` (the registry, `isExpired`).
